留言板和小爱都上线之后，我一直没开自动回复。原因很简单：**一个会说话的 AI 出错，比一个不会说话的 AI 危险得多**。

她说的每句话都挂着站点的名义。回得不好，最多是尴尬；回错了，是整站替我说了一句不该说的话。

所以这次开启的顺序是反的：先把「什么时候不许说话」写清楚，最后才允许她开口。

## 什么情况下不说话

`autoReplyTo` 进去之后是一串 return，全在前面：

```ts
// 回复范围：默认只回顶层。楼里访客之间聊起来，AI 凑上去插嘴很怪
if (ar.scope === 'top' && root.parent_id != null) return;

// 路径闸：blockPaths 优先，allowPaths 为空表示不限
if (!autoReplyPathAllowed(settings, pathOf(root.post_slug))) return;

// 小爱自己说的话不触发
if (String(root.author ?? '').trim() === me.author) return;

// 站长本人说的话不触发
if ((root.acc_role ?? '') === 'admin') return;
```

四条，每条都有一个很具体的画面：

- **不接楼中楼。** 两个访客在底下聊起来了，第三个人（AI）挤进来接一句，那个场面谁见都别扭。顶层留言才是「对站点说话」。
- **路径闸。** 有些页面不该有 AI 的声音 —— 申请页、后台相关的说明页。反过来也留了口子：只填白名单就是「只有这几页回」。
- **不接自己。** 她说过的话如果又触发一次，会自己跟自己聊起来。
- **不接站长。** 这条是我最在意的。后台测试、自言自语、随手记一句，每条都长出一句「小爱回复了清吾」，评论区很快就变成我和她的对话记录。判据用的是账号角色，不是昵称 —— 昵称可以改，角色是事实。

然后是幂等：

```ts
// 已经有小爱的回复 → 手回过的也算，不重复
const has = await env.DB.prepare(
  'SELECT 1 AS x FROM comments WHERE parent_id = ? AND author = ? LIMIT 1',
).bind(commentId, me.author).first();
if (has) return;
```

注意判据是「这条留言下面有没有以小爱名义发的回复」，而不是「有没有自动回复记录」。这样我手动替她回过的，也不会再被自动回一遍。**幂等不依赖新表**，新表没建也能生效。

最后一道是垃圾评论：

```ts
if (status !== 'spam') ctx.waitUntil(autoReplyTo(env, id, { verdict: mod }));
```

被判成垃圾的不叫她来接话 —— 不能让她嘴里复述一条广告。

## 她不该说的话

就算该回，内容也得过一遍筛子。`guardAutoReply` 做的是输出侧拦截：

```ts
if (/https?:\/\//i.test(t)) return null;
if (/\bwww\.[a-z0-9-]+(\.[a-z0-9-]+)+/i.test(t)) return null;
if (/[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}/i.test(t)) return null;
if (/(?:\+?\d[\s-]?){7,}/.test(t)) return null;
if (/(微信号|加微信|加我微信|扫码|二维码|私聊|站内信|联系方式)/.test(t)) return null;
```

链接、邮箱、连续七位以上的数字、微信相关词 —— 命中任意一条，这句话直接丢掉，不落库。

这不是防她「想干坏事」，是防她被利用。评论区是个公开的、谁都能写的地方，只要有人能诱导她输出一条链接或一个联系方式，这个站就成了一个免费的、有信誉背书的引流渠道。

代价是她的回复里不能提任何网址。可以接受 —— 一个吐槽机器人的回复本来也不需要链接。

## 最阴的一种：上游返回 200，内容是报错

这个是开后第二天才补的，也是整套规则里我觉得最值得单独说的一个。

上游 API 有个习惯：它不一定抛错。有时候 HTTP 200 回来一段正文：

```
接口调用失败，请稍后重试
服务繁忙，rate limit 429
invalid api key
```

或者模型把自己当客服，把提示词里那些没人看的诊断信息原样复述出来。

这些话一旦落库，性质就变了 —— 变成**「爱弥斯」在公开评论区告诉访客站点坏了**。比干脆不说话糟得多，而且我多半过很久才会发现，因为没人会来告诉我「你的机器人在说你的服务器挂了」。

所以加了一道检查：

```ts
function looksLikeErrorText(raw: string): boolean {
  const t = String(raw ?? '').trim();
  if (!t) return true;
  return ERROR_TEXT_RE.some((re) => re.test(t));
}
```

难的是**不误伤**。`ERROR_TEXT_RE` 里刻意做了三条排除：

- **不认语气词。** 「抱歉」「不好意思」是正常人说话的开头，不能因为出现「抱歉」就当成报错。
- **不认单个数字。** 访客在文章下面说「这个 500 字的段落」「502 房间」都很正常，不能看到数字就判。
- **认的是结构，不是关键词。** 不是「出现 error 就算」，而是「以 error/错误/失败 开头并跟冒号」「JSON 形态的错误体」「状态码 + 错误短语」「配额不足」「内部标记漏进正文」这些有明确形态的东西。

比如这几条：

```ts
/^\s*[\[【(（]?\s*(error|exception|错误|异常|失败|报错)\s*[\]】)）]?\s*[:：]/i
/\b(unauthorized|too many requests|rate[_\s-]?limit|quota (exceeded|exceed)|insufficient_quota)\b/i
/【[^】]{0,12}(系统|核查|待审|提示词)[^】]{0,12}】/
```

最后那条是防内部标记漏出来的。我给她喂的上下文里有「【友链申请 · 系统实地核查】」这类结构化标记，万一模型把它抄进回复，那句「系统核查」就成了公开信息。

## 成本：一次回复只判两遍

上一版有个浪费：同一条留言，提交时判一遍（决定要不要拦），起草前又判一遍。

现在的做法是把提交时那次的结果传下去：

```ts
ctx.waitUntil(autoReplyTo(env, id, { verdict: mod }));
```

```ts
/**
 * `opts.verdict` 是提交时那一次判定的结果：
 * 传进来就复用，不再对同一条留言重判一遍 —— 一次自动回复因此只花 2 次 judge
 * （提交 1 + 输出 1），而不是 3 次。传 null 也算「判过了、但那次没判出结果」。
 */
```

`null` 和 `undefined` 在这里语义不同，这个小设计值得留着：`undefined` 是「没判过，你自己去判」，`null` 是「判过了，没结果，别重复花钱」。

## 额度：单访客有上限，全局没有日限

这里有个刻意的不对称。

**单访客有额度。** 一个人一天能触发几次自动回复是有限制的，超过就不回了。防的是同一个人刷屏把额度吃光。

**全局没有日总量。** 这条是站长明确要求的 —— 他不想因为「今天回复够多了」这种理由让小爱突然不吭声。

但有个东西不能跟着删：

```ts
// 花费的硬闸仍在 quotaGate（AI_DAILY_LIMIT，默认 300 次/通道/天），
// 那是防 key 被刷的底线，和运营口径无关，别一起删。
```

这层是防 key 被盗用的：key 在服务器上，万一漏了，至少一天 300 次能兜住。**运营口径可以商量，安全底线不能。** 两个数字长得很像（都是「次数限制」），但服务的是完全不同的目的，混在一起删过一次就懂了。

## 时机：不要在请求路径上 await

```ts
/**
 * **永远不要 await 在请求路径上** —— 调用方一律 `ctx.waitUntil(autoReplyTo(...))`。
 */
```

访客点了「发表」，他要的是「发出去了」这个确认，不是「AI 想好了怎么回」。一次模型调用少说两三秒，多则十几秒 —— 挂在请求路径上，评论区就成了一个会卡十几秒的表单。

`waitUntil` 让这次回复挂在请求生命周期之后跑，用户立刻拿到成功响应。副作用是它**没有重试**：进程被回收就丢了。所以这个函数不抛错、也不返回有意义的值，结果全落库（`comments` 和 `auto_reply_log`），靠数据说话。

## 配置每轮现读

```ts
// 设置每轮现读：后台刚把它关了，下一条留言就该不说话
const settings = await loadSettings(env);
```

不缓存。每次多一次数据库读，换来的是「关掉立刻生效」。

这条是踩过一次才想明白的：如果设置缓存在进程里，我在后台关掉开关，接下来几条留言她还会继续说话 —— 而且我完全没法判断是「没生效」还是「刚好有人在写」。**开关这种东西，生效时间必须是确定的。**

## 写在最后

做这一块最大的收获不是 prompt 怎么写，而是把「AI 功能」当成一个**有输出权限的组件**来设计。

一个会自动说话的功能，它的失败模式不是「不说话」，而是「说了不该说的」。所以规则的重心全在否决上：

- 选择场景（只回顶层、路径白名单）
- 选择对象（不接自己、不接站长、不接垃圾）
- 选择内容（无链接、无联系方式）
- 选择形态（不像人话就不发）
- 选择时机（不阻塞用户）
- 保留底线（防刷配额不能删）

做完这些，她才敢被打开。

至于回复本身像不像人 —— 那是最后才需要考虑的问题。而且说实话，留言板这种地方，一句「这个我也卡了很久」比一段漂亮的总结更像人。
