老版音乐页是两张卡片拼的：左边封面，右边歌词。13 首歌，得先点开右边那个标签页才看得到自己在听什么。

这次照桌面播放器的样子重排：上半是正在播放，右边整片让给歌词，曲库挪到下面去。但真正花时间的不是版式，是那个「跟着唱」的观感 —— 一句一句滚过去太普通了，想要的是**这一句里，字一个一个亮起来**。

## 第一个问题：LRC 没有字级时间

标准 LRC 长这样：

```
[00:12.34]穿过人潮 走到这里
[00:16.80]灯还亮着 就别停下
```

一行一个时间戳，行内哪几个字对应哪一秒，文件里根本没写。

正规做法是拿强制对齐（forced alignment）把音频和文本重新对齐一遍，拿到每个字的起止时间。Whisper、Montreal Forced Aligner 都能做。我没走这条路，原因很实际：**13 首歌要跑多久、跑坏了谁来核对**。逐字对齐对音乐是很不友好的任务 —— 有伴奏、有和声、有拖长音，模型很容易把整句压成一团。做完还得一首一首听过去校对，这活儿比写代码烦。

所以我用了估算：

```js
function progressAt(lines, i, t, total) {
  if (i < 0 || i >= lines.length) return 0;
  const start = lines[i].time;
  const end = lines[i + 1]?.time ?? Math.max(total, start + 3);
  const span = end - start;
  if (!Number.isFinite(span) || span <= 0.15) return 1;
  return Math.min(1, Math.max(0, (t - start) / span));
}
```

一句话：**这一行有多长（到下一行的时间差），字就按这个时长平均分**。唱到 30% 就亮三成，唱到 70% 就亮七成。

三个细节值得说：

- **末行用总时长兜底。** 最后一句后面没有「下一行的时间」，不兜底的话 `end` 是 `undefined`，整句永远不亮。
- **行与行之间不留空档。** 上一行的终点就是下一行的起点，否则间奏前面那一句会停在半格，看着像卡住。
- **`span <= 0.15` 直接判 1。** 有些 LRC 里连着两行时间戳几乎相同（合唱、念白），除出来会是一个巨大的数，进度瞬间跳满。这种行直接当「已经唱完」更自然。

实测下来误差不到 0.2 秒。对四四拍的流行歌，人眼根本分辨不出来 —— 眼睛跟着亮的字走，不会觉得「慢半拍」。

这不是精确，是**够用**。

## 擦色：为什么写一个变量，而不是直接写 clip-path

逐字填充的实现很朴素：一层底字，一层绯红色的同款文字盖在上面，用 `clip-path` 把它裁成「唱过的部分」。

第一版是每帧直接算 `el.style.clipPath = 'inset(0 ' + (1 - p) * 100 + '% 0 0)'`。看着没问题，实际有个很讨厌的现象：

**唱过的句子，一直红着。**

因为行离开「当前」状态之后，没有任何人去复位它的内联 `clip-path`。它停在最后一次算出来的进度上 —— 一句唱了 40% 就被切走的歌词，会永远保留那 40% 的红。滚回去一看，满屏都是半红的旧句子。

改法是把「进度」和「裁剪」拆开：

```js
el.style.setProperty('--p', progressAt(lines, i, t, duration).toFixed(4));
```

```css
.q-ly__fill {
  clip-path: inset(0 calc((1 - var(--p, 0)) * 100%) 0 0);
}
.q-ly[data-on='0'] .q-ly__fill {
  clip-path: inset(0 100% 0 0);
}
```

颜色只在 `--p` 上表达，**裁剪规则是活的**：只要这行不是当前行，CSS 强制把它裁到 100%（也就是什么都不显示）。不需要谁去「记得复位」，因为没有状态可以残留。

还有一个更隐蔽的 bug，是宽度惹的。

第一版 `.q-ly` 是 `width: 100%`。擦色百分比按元素宽度算，而容器有 775px、文字只有 297px —— 于是进度到 38% 的时候，`inset(0 62% ...)` 裁到的位置早就过了文字末尾，**整句一下子全红**。你会以为是自己时间算错了，其实是长度标准不一致。

```css
.q-ly {
  /* ⚠️ 必须是 fit-content：擦色的百分比按「元素宽度」算 */
  width: fit-content;
  /* 同时必须限宽：3D 透视会把右端放大 1.3~1.5 倍 */
  max-width: min(100%, 26rem);
}
```

`fit-content` 让元素宽度等于文字宽度，`--p` 才真的等于「唱到第几个字」。限宽是另一件事 —— 后面讲 3D 时它才显出必要性。

## 滚动：不用 scrollIntoView，也不用 scrollTop

歌词要滚动，最自然的是 `scrollIntoView()`。但它有个副作用：**会连带滚动所有可滚动祖先**。歌词轨的祖先里有整个页面，于是每次换行，页面都跟着抖一下。

退一步改用 `scrollTop`，页面是不动了，但滚动位置没法做缓动 —— 歌词是「跳」过去的，一格格闪。

最后用的是最笨的一招：内层轨 `translateY`，父级 `overflow: hidden`。

```jsx
<div className="q-ly-box">           {/* overflow: hidden; 遮罩 */}
  <div className="q-ly-track" style={{ transform: `translateY(${-shift}px)` }}>
```

位移只发生在轨自己身上，外面稳如泰山，而 `transform` 天生能上过渡曲线。

配套的还有一条：**行高必须固定，当前行只做 `scale`**。

如果让当前行变大字号来强调，轨的总高度就会变，后面所有行的 `offsetTop` 全跟着变，居中计算每换一行就抖一次。`transform: scale()` 不改占位，视觉上放大、布局上没动，这才是安全的做法。

## 3D：轴为什么只能钉在左边

纵深是靠一层倾斜做的：

```css
.q-ly-tilt {
  transform: perspective(660px) rotateY(-18deg) rotateX(3deg) rotateZ(2.2deg);
  transform-origin: left center;
}
```

`rotateY(-18deg)` 让整片歌词往右前方转过来：每句开头几乎不动，越往右越靠近镜头。桌面端看着就像歌词浮在一个斜面玻璃上。

这里有个必须记住的结论：**轴只能钉左边**。

我一开始试过钉右缘（`transform-origin: right center`），想让左边往后缩。结果长句被透视推到面板左侧以外，直接被遮罩切掉半个字。旋转的轴在哪，另一边就会被拉出去 —— 钉右边就等于让左端承受最大的位移。

`perspective` 给的是 660px。试过 900px，那点宽度差几乎看不出纵深，等于白转；再小到 500px 又会把字拉得太夸张。660 是「看得出来但不滑稽」的那一档。

手机上这个倾斜直接关掉：

```css
@media (max-width: 767px) {
  .q-ly-tilt { transform: none; }
}
```

屏幕只有 20rem 宽，转 18° 会把字压小、右端还容易切边。**手机上要的是看得清，不是纵深。**

还有个 DOM 结构上的小事：倾斜层和位移层必须是两层。

```jsx
<div className="q-ly-tilt">                    {/* 3D */}
  <div style={{ transform: `translateY(${-shift}px)` }}>  {/* 滚动 */}
```

`transform` 是覆盖不是叠加，写在一个元素上，`translateY` 会把倾斜顶掉。

## 景深：远的虚、近的实，是按距离分档

不是套一层渐隐遮罩，而是每一行按「离当前句多远」单独处理：

| 距离 | 模糊 | 透明度 | 缩放 |
|---|---|---|---|
| 1 行 | 1.2px | 0.68 | 0.975 |
| 2 行 | 2.6px | 0.48 | 0.95 |
| 3 行 | 4px | 0.32 | 0.925 |
| 3 行以上 | 5.5px | 0.2 | 0.9 |

```jsx
const dist = anchor < 0 ? i + 1 : Math.abs(i - anchor);
<div data-dist={dist > 3 ? 'far' : String(dist)} />
```

只有 `filter: blur` + `opacity` 真正做出「镜头虚化」的味道。一层渐变遮罩只会让字变淡，不会变糊 —— 一眼就能看出是假的。

`far` 那一档有一条特别规则：**不加过渡**。

```css
.q-ly[data-dist='far'] {
  transition: none;
}
```

一首歌三十九行，如果每一行都参与 `filter` 的过渡，换行那一刻有几十个元素同时动过滤器，帧率直接掉下去。反正它们在遮罩边缘、本来就看不清，「跳」和「渐变」肉眼没区别。**把过渡留给看得见的那几行。**

手机上同样的 blur 值会把后几行直接糊没，所以整体减半（1 行 0.7px、far 3px）。

## 手动滑动：必须临时关掉景深

歌词轨支持滚轮和拖动翻看。这里遇到一个逻辑上的矛盾：

景深是「离当前唱到那句多远」算的。但你手动翻到很远的地方时，眼前每一行离当前句都很远 —— **全是 far 那档，5.5px 模糊加 0.2 透明度，什么都看不见**。

所以接管期间必须换一个焦点。做法是：翻的时候按「视口正中那一行」算景深。

```js
// 接管期间：算出视口正中是哪一行，景深跟着它走
const center = shift + box.clientHeight / 2;
```

中间那行清楚，上下照样渐隐渐糊 —— 纵深保住了，眼前也不至于一片糊。

这个「焦点」和「当前唱到第几句」是两个不同的概念，代码里分开存（`focus` 和 `active`）。自动跟随时 `anchor = active`，手动接管时 `anchor = focus`。混成一个变量，就会出现「翻走之后列表还在按音频高亮」的错位。

停手 6 秒自动回到当前句，右下角也给一个「回到当前句」的按钮。按播放键立刻回位 —— 你的意图明显是「从这儿接着听」，不该还停在刚才翻到的地方。

## 一个指针捕获，让点击整整失效了一版

「点歌词跳到那一句」这个功能，第一版完全不工作。点下去毫无反应，日志里也没有任何事件。

原因是 `onPointerDown` 里写了 `setPointerCapture`。

指针捕获的作用是「就算手指移出元素，后续事件也继续发给它」。听起来是拖拽的标准做法。但捕获之后，`pointerup` 会被重定向到容器，**浏览器随之把随后的 `click` 也派发给容器**。行上的 `onClick` 永远收不到 —— 因为它不是点击目标了。

改法是**只有真的开始拖了才捕获**：

```jsx
const onPointerDown = (e) => {
  dragRef.current = { y: e.clientY, base: shiftRef.current };
  draggedRef.current = false;
  setUserShift(shiftRef.current);
  /* ⚠️ 这里不能 setPointerCapture：一旦捕获，click 会被派发给容器 */
};

const onPointerMove = (e) => {
  const dy = d.y - e.clientY;
  if (!draggedRef.current && Math.abs(dy) > 6) {
    draggedRef.current = true;
    e.currentTarget.setPointerCapture?.(e.pointerId);   // 拖起来了才捕获
  }
};
```

6px 的阈值是给手指抖动的余量。小于它就是「点」，大于它才是「拖」。

还有一个配对的处理：拖动结束后松手，`draggedRef` 还是 `true`。这一次松手如果刚好落在某一行上，浏览器还是会补一个 `click` —— 于是「拖完歌词，顺便跳到了某一句」。所以在 `onClick` 里要先检查这个标志：

```jsx
onClick={() => {
  if (draggedRef.current) { draggedRef.current = false; return; }
  onSeek(ln.time);
}}
```

两个 `draggedRef.current = false` 各管一件事：`onPointerDown` 里管「新一次交互开始」，`onClick` 里管「这次点击是拖动的尾巴」。漏掉后一个，拖拽就会莫名其妙地跳歌。

## 容器高度会变，所以量尺寸不能立刻量

播放中静置 4.5 秒，控制条、音量、时间会一起收起来，把画面留给封面。这个动画让整个舞台矮了 130px —— 歌词容器的高度跟着变，居中位置也就得重算。

于是挂了 `ResizeObserver`。第一版直接在回调里 `measure()`，结果是**位移看起来卡住不动**。

因为收起动画要跑 340ms，这期间每帧都触发一次回调，每帧都重设一次 `translateY`。过渡被不停打断重来，看着就像黏在半路。

改成尾部防抖：等尺寸稳定下来再量一次。

```js
const ro = new ResizeObserver(() => {
  window.clearTimeout(t);
  t = window.setTimeout(() => measureRef.current(), 120);
});
```

`120ms` 比动画短、比单帧长，落在「动画结束了」和「用户察觉延迟」之间。

顺带一个小决定：**前奏期不居中第一行**。

还没唱到第一句时（`active = -1`），第一版把第一行居中，觉得「这样才对称」。但居中意味着它正好落在顶部遮罩的淡出区 —— 前奏十几秒里，首句几乎看不见，像是缺了一句。改成 `translateY(0)` 从头排，第一行就在上方清晰区里待着。

## 写在最后

这一块没有特别高深的技术，全是一些「看起来该这样做、实际不行」的地方：

- 没有字级时间戳 → 用行时长除以字数估，误差 0.2 秒内够用。
- 擦色永远不复位 → 把状态交给 CSS 变量，用选择器强制收。
- 百分比按容器宽算 → 元素必须 `fit-content`，否则 42% 就填满。
- 指针一按下就捕获 → 点击事件被容器吃掉，拖 6px 才该捕获。
- 尺寸一变就重量 → 过渡被打断成卡顿，要等它稳定。

共同点是：**它们都不报错**。表现都是「有时候不对」「看着像卡住」「点了没反应」，而这类问题最耗时间。

真正让我改变判断的是两件事。一是「够用」比「精确」重要 —— 我差点为了逐字对齐去跑一遍模型，而 0.2 秒的估算误差根本没人看得出来。二是**该关就关**：手机上关掉 3D、远处那几十行不参与过渡、手动翻看时换掉景深锚点。这些「减掉」比「加上」更决定它好不好用。
