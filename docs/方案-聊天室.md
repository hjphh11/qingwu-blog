# 方案 · 长亭（聊天室）

> 目标：给 [www.qingwu.ink](http://www.qingwu.ink) 加一个「有人在场」的聊天室，**并且和友站的聊天室联通**。  
> 名字：**长亭**（十里一长亭，供行人歇脚、相遇。每个人从不同的路上来，在这里碰面）。  
> 参考对象：听雨茶室（rainzt.cn/chat）。

---

## 一、参考对象拆解（这次结论改了）

第一版方案我判断「不做互联」，那是错的 —— 你要的就是互联。重新拆一遍：

| 他们的做法                | 判断                          |
| -------------------- | --------------------------- |
| 独立 `/chat/` 页面，留言页保留 | ✅ 学。留言是「一次性招呼」，聊天是「在场」      |
| 2 分钟撤回 + 留一行提示       | ✅ 学。成本极低                    |
| 「上次看到这里」未读分隔         | ✅ 学。一条 read 游标              |
| 消息轻回应                | ✅ 学，直接用你的表情包，不另做小猫          |
| @ 提及 + 邮件/浏览器通知      | ✅ 学。`mail.ts` 现成            |
| 草稿保存 + 失败重试          | ✅ 学。纯前端                     |
| Markdown 小文章         | ✅ 学。`richText.ts` 现成        |
| AI 24 小时巡查           | ✅ 学。`moderateComment` 现成    |
| 免登录填邮箱昵称             | ⚠️ 不学。你有 `accounts`，登录即进更干净 |
| 已读名单                 | ❌ 不做。群聊级功能，个人站里只会变成社交压力     |
| **Matrix 大厅 + 桥接**   | ✅ **要做，但走「接入已有大厅」而不是「自建」**  |

## 二、互联：三条路，只有一条划算

这是整份方案里唯一需要你亲自做决定的地方，因为另外两条的成本差一个数量级。

### 路径 A · 接入听雨的 Matrix 大厅（推荐）

现状：听雨已经在跑一个公开大厅 `#lobby:detached.online`，homeserver 是 `matrix.rainzt.cn`，  
里面已经有 **四个站**：听雨茶室、雪宝的站点（daily.yybb.us）、冷汐的杂货铺（lengxiqwq.com）、Somoe。

你只需要一个**共享转发账号**——听雨文档里明说「可以免费提供一个指定用于本站互联的 Matrix 转发账号，  
并为它登记站点来源」。拿到之后：

- 出站：`PUT /_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId}`
- 入站：`GET /_matrix/client/v3/sync?since=<游标>`
- 你的机器上**不需要跑任何新服务**，只有一个 HTTP 客户端

**代价**：所有清吾茶友共用同一个 Matrix 身份，发言人靠消息正文里的元数据区分；  
消息会经过听雨的 homeserver（他能看到，也会做巡查）。

### 路径 B · 自建 homeserver，每人一个真 Matrix 账号

装 Synapse 或 Conduit，每个人有 `@xxx:matrix.qingwu.ink`。身份最干净，还能用任意 Matrix 客户端登录。

**代价**（这是劝退点）：

- 香港机多一个常驻服务，内存起步 1G+，还要 Postgres
- 联邦要开 8448 端口 + TLS + DNS SRV 记录，`fail2ban` 和限流规则要重做一遍
- 一个个人博客为聊天室养一套 IM 后端，运维成本超过站点本身

> **除非你打算把聊天室做成一个正经产品，否则不值得。**

### 路径 C · 自建轻量协议（站对站直接对接）

每站一个 `POST /chat/federate` + HMAC 签名。技术上最简单、最可控。

**代价**：没有生态。听雨、雪宝、冷汐都在 Matrix 上，你要么说服他们为你的协议改造，要么自己玩。  
**等于建一个只有自己一个成员的联邦**。

### 结论

**走 A。** 互联的价值在「有人」，不在「技术纯洁」。四个站已经在大厅里，你去就有话说；  
自己建一套再拉人，路径长十倍。

一个前置事实：**你得先有一个 Matrix 账号（或邮箱）去联系听雨申请**。这一步是人和人的事，代码替不了。

## 三、架构：本地优先，Matrix 是「另一个出口」

这是最重要的设计判断。三种做法：

| 做法               | 问题                                                          |
| ---------------- | ----------------------------------------------------------- |
| Matrix 当主库，本地只渲染 | Matrix 一挂，你连自己的聊天记录都看不到；历史要靠 `/sync` 慢慢拉；审核/搜索/撤回全要绕 Matrix |
| **本地当主库 + 桥接转发** | ✅ 采用                                                        |
| 双主（同时写两边）        | 一致性最难，撤回和删除要处理两套                                            |

**本地 SQLite 是唯一事实来源。** Matrix 挂了、token 失效、联邦断连——聊天室照常能聊，只是暂时不互联。

```
          ┌─────────────── 浏览器 /chat/ ───────────────┐
          │  每 2.5s GET /api/chat/poll?after=<id>      │
          └──────────────────┬──────────────────────────┘
                             │ nginx /api/ → :8787
                             ▼
                    worker/src/chat/*
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
            SQLite（主库）        chat_outbox（出站队列）
                  ▲                     │
                  │                     ▼
            chat_sync（游标）    Matrix C-S API
                  │                     │
                  └─────────────────────┘
                       桥接循环（cron，10s）
```

### 3.1 传输：轮询 2.5s，不用 WebSocket

理由不变：生产是 `wrangler dev --local` 常驻（`qingwu-api.service`），  
一 restart 所有 WS 连接同时断；轮询只是静默重试一次。

接口按**增量**设计（`after=id`），将来换 SSE/WS 只换传输层，消息格式不动。

### 3.2 桥接循环跑在哪

workerd 没有常驻循环。两个选择：

- **cron 服务**（推荐）：`qingwu-chat-bridge.timer`，每 10 秒跑一次同步脚本
- **poll 顺手推**：有人开页面时顺带同步一步。没人看页面时不同步，跨站消息会滞后

**推荐：cron 为主（10s），poll 只读本地库不碰网络。** 职责清楚，排障简单。  
代价是跨站消息最多慢 10 秒——对「不同站的两个人聊天」这个场景完全够。

> 如果以后觉得慢，再加「poll 顺手推」作为加速：用 `chat_sync.lock_until` 抢锁防并发，  
> 逻辑不用改，只是多一个触发点。

## 四、数据模型（9 张表，`0026_chat.sql`）

```sql
-- 消息。单一大厅，不设房间
CREATE TABLE chat_messages (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id    INTEGER,                    -- 本地消息才有；远程为 NULL
  body          TEXT    NOT NULL,           -- 原文（Markdown 子集 + 表情 token）
  kind          TEXT    NOT NULL DEFAULT 'text',   -- text | image
  reply_to_id   INTEGER,
  mentions      TEXT,                       -- JSON：[3,7] = 本地账号 id
  status        TEXT    NOT NULL DEFAULT 'visible', -- visible|pending|spam|deleted|recalled
  ts            INTEGER NOT NULL,
  ip_hash       TEXT,

  -- 互联（v2）
  origin        TEXT    NOT NULL DEFAULT 'local',  -- local | remote
  remote_sender TEXT,                       -- 完整 Matrix 用户 ID
  remote_nick   TEXT,                       -- 对方昵称（显示用）
  remote_avatar TEXT,
  remote_site   TEXT,                       -- 「冷汐的杂货铺」，前端挂「来自 XX」
  matrix_event_id TEXT,                     -- 去重 + 撤回映射
  matrix_txn_id   TEXT
);
CREATE INDEX idx_chat_id    ON chat_messages(id DESC);
CREATE INDEX idx_chat_acc   ON chat_messages(account_id, ts DESC);
-- matrix_event_id 唯一：重连补拉时挡住重复导入（NULL 不参与，本地消息不受影响）
CREATE UNIQUE INDEX idx_chat_evt ON chat_messages(matrix_event_id) WHERE matrix_event_id IS NOT NULL;

CREATE TABLE chat_reactions (
  message_id INTEGER NOT NULL, account_id INTEGER NOT NULL,
  emoji TEXT NOT NULL, ts INTEGER NOT NULL,
  PRIMARY KEY (message_id, account_id, emoji)
);

CREATE TABLE chat_reads (
  account_id INTEGER PRIMARY KEY,
  last_read_id INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

CREATE TABLE chat_presence (
  account_id INTEGER PRIMARY KEY,
  last_seen  INTEGER NOT NULL              -- poll 顺手节流写（>20s 一次）
);

CREATE TABLE chat_bans (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id INTEGER, ip_hash TEXT,
  until INTEGER, reason TEXT, created_at INTEGER NOT NULL
);

-- ——— 互联专用 ———
-- 出站队列。本地原创消息先落这里，桥接按 FIFO 发
CREATE TABLE chat_outbox (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  message_id  INTEGER NOT NULL,
  op          TEXT    NOT NULL DEFAULT 'send',  -- send | redact | react
  txn_id      TEXT    NOT NULL,                 -- 幂等键，重试沿用同一个
  status      TEXT    NOT NULL DEFAULT 'queued',-- queued|sending|done|failed
  tries       INTEGER NOT NULL DEFAULT 0,
  next_at     INTEGER NOT NULL DEFAULT 0,       -- 退避时间
  last_error  TEXT,
  created_at  INTEGER NOT NULL
);
CREATE INDEX idx_outbox_due ON chat_outbox(status, next_at);
CREATE UNIQUE INDEX idx_outbox_txn ON chat_outbox(txn_id);

-- 入站游标（一行）。lock_until 防并发同步
CREATE TABLE chat_sync (
  id         INTEGER PRIMARY KEY CHECK (id = 1),
  room_id    TEXT,
  since      TEXT,                          -- Matrix next_batch
  lock_until INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

-- 已收红删。**防止「先收到撤回、后收到原文」时把消息补回来**
CREATE TABLE chat_redactions (
  event_id   TEXT PRIMARY KEY,              -- 被撤回的 Matrix 事件 ID
  ts         INTEGER NOT NULL
);

-- 桥接日志（排障，只留 7 天）
CREATE TABLE chat_bridge_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL, level TEXT, msg TEXT
);
```

> **`chat_redactions` 这张表看着多余，其实是文档里特意点出的坑**：  
> 「先收到红删也要记住它，避免重连后把原文补回来」。没有它，一次断线重连就会让被撤回的消息复活。

消息永不物理删除（`status` 软删），和评论一致。

## 五、接口

| 方法   | 路径                                   | 说明                              |
| ---- | ------------------------------------ | ------------------------------- |
| GET  | `/chat/history?before=<id>&limit=50` | 首屏 / 向上翻页                       |
| GET  | `/chat/poll?after=<id>`              | 增量 + 在线人数 + `recalled:[id]`     |
| POST | `/chat/send`                         | `{ body, replyTo?, mentions? }` |
| POST | `/chat/:id/recall`                   | 2 分钟内、只能自己的                     |
| POST | `/chat/:id/react`                    | 再点一次取消                          |
| POST | `/chat/read`                         | `{ lastId }` 更新游标               |
| GET  | `/chat/bridge-status`                | **公开只读**：桥接是否在线、待发队列长度          |
| POST | `/admin/chat/bridge/pause`           | 站长暂停本方转发（互联合规要求）                |

`poll` 响应：

```json
{
  "ok": true,
  "messages": [ ... ],
  "recalled": [12, 15],
  "online": 5,
  "bridge": { "connected": true, "pending": 3 }
}
```

> 两个容易漏的字段：`recalled`（不推它，别人屏幕上的撤回消息永远摘不掉）、  
> `bridge`（互联状态要能一眼看到，不然「为什么我发的消息对方没收到」会变成玄学）。

## 六、互联协议细节

### 6.1 发出去的消息长什么样

**双格式**。结构化字段给懂的实现，正文协议头给只认正文的：

```json
{
  "msgtype": "m.text",
  "body": "[ID:小明];[URL:https://www.qingwu.ink/avatar/x.webp]\n\n下午好，我从清吾过来。",
  "format": "org.matrix.custom.html",
  "formatted_body": "下午好，我从清吾过来。",
  "org.tea-room.bridge": {
    "version": 1,
    "site": "https://www.qingwu.ink",
    "actor": { "id": "qingwu-u12", "nick": "小明" },
    "text": "下午好，我从清吾过来。"
  }
}
```

三个要点：

- `actor.id` 用 `qingwu-u<accountId>`，**改名、换头像、重装都不影响身份**。  
  不要用昵称当键——听雨文档里明确说了那是旧协议的限制（同名会撞、改名产生新身份）。
- `body` 首行的协议头是兼容层，听雨兼容这种写法，且头像只能靠它带过去。  
  （v1 结构化字段目前只读 ID / 昵称 / 正文，头像要双方扩展，所以 HTTP 地址必须留在正文头上。）
- `site` 字段只是便于识别；**来源以接收端配置为准**，不要指望它被信任。

### 6.2 Matrix 显示名

听雨约定的格式是 `昵称 · 站点名`。清吾这边用：

```
小明 · 清吾
```

（例子：`朝朝听雨 · 听雨茶室`、`遇见 · 冷汐的杂货铺`、`雪中来客 · 雪宝的站点`）  
中间是间隔点 + 两侧半角空格。站点名用正式名，别用「长亭」——长亭是房间名，  
混进「XX · 长亭」会让别站的人以为又来了一家叫长亭的站。

### 6.3 收到的消息怎么落库

```
/sync 拿到 to_device / timeline 事件
  ├─ 忽略自己的回声（sender == 本方转发账号 且 actor.id 以 qingwu- 开头）
  ├─ m.room.message
  │    ├─ 优先读 org.tea-room.bridge v1（id / nick / text）
  │    ├─ 没有就读正文协议头 [ID:..];[URL:..]
  │    ├─ 都没有就按 Matrix 成员资料（display_name / avatar）
  │    └─ 落库 origin='remote'，matrix_event_id 唯一索引挡重复
  ├─ m.room.member → 更新成员名册（不建本地账号）
  ├─ m.room.redaction → 软删对应行 + 写 chat_redactions
  └─ 成功后推进 since（**入库之后**才推进）
```

### 6.4 双向映射表

| 本地动作      | Matrix 动作                                                  |
| --------- | ---------------------------------------------------------- |
| 发消息       | `PUT /rooms/{id}/send/m.room.message/{txnId}`，存 `event_id` |
| 撤回（2 分钟内） | `PUT /rooms/{id}/redact/{eventId}/{txnId}`                 |
| 收到别人的撤回   | 按 `matrix_event_id` 找行，软删                                  |
| 表情回应      | 暂不互联（v1 只同步文字，减少兼容面）                                       |

### 6.5 限流（听雨的硬要求）

听雨文档里把这条列为接入前提，原文要求：**每个发言身份限频 + 整站出站队列限额 + 文字图片都算 + 共享账号按原发言人分别计数 + 超限给明确等待提示 + 不许攒一堆再一次性发**。

所以：

| 层级            | 额度                                        | 超了怎么办             |
| ------------- | ----------------------------------------- | ----------------- |
| 单个茶友（本地）      | 间隔 ≥1.2s，≤15 条/分钟                         | 前端提示「慢一点」，服务端 429 |
| 单个茶友（出站）      | 同上，按 `account_id` 计                       | 这条留在队列里等          |
| 全站出站          | ≤30 条/分钟（保守）                              | 队列 FIFO 排队，不合并批量发 |
| Matrix 返回 429 | 按 `Retry-After` 退避，兼容旧字段 `retry_after_ms` | 逐步拉长间隔            |

### 6.6 失败模式

| 故障            | 表现         | 处理                                        |
| ------------- | ---------- | ----------------------------------------- |
| token 失效（403） | 出站全失败      | 标记 `bridge.connected=false`，后台红标，**本地照常** |
| 房间别名解析失败      | 一个事件都拉不到   | 暂停同步，后台显示「房间 ID 待核对」                      |
| 联邦断连（超时）      | `/sync` 卡住 | 指数退避，最长 5 分钟一次                            |
| 重复导入          | 同一条出现两次    | `matrix_event_id` 唯一索引挡住                  |
| 先收撤回后收原文      | 撤回的消息复活    | `chat_redactions` 表兜住                     |

## 八、审核：本地清单 + 异步后审

⚠️ 完整清单见 `docs/审核清单-聊天室.md`。

聊天不能同步审核（每条卡 200~350ms 没人愿意说话），所以分两道：本地清单常数时间过一遍，  
**不命中直接放行**，之后异步走 Jev。命中 → 按 `block` / `hold` / `flag` / `pass` 四种动作处置。

`hold` 是关键：疑似但可能误伤的消息落 `pending`，**自己看得见、别人看不见**，AI 判完通常一两秒转正，  
本人无感。直接拒绝会把新来的人赶走。

**互联场景要加一条**：本地 `hold` 的消息**不进 outbox**。等判定通过再入队，  
否则你会在别的站上留下一串撤回不掉的痕迹。

## 九、合规与边界

### 站点已备案，互联带来三件事

1. **必须提示同步范围**：输入框附近常驻一句「这里的公开消息会同步到 Matrix 及其他互联站点」。  
   听雨文档把这条列为接入验收项。
2. **站长必须能一键暂停转发**：`/admin/chat` 上一个开关，出站队列立刻停。  
   误转发、刷屏、账号被盗都用得上。
3. **他人撤回请求要能响应**：友站要求删掉某条跨站消息时，本地要有对应入口。

> 内容会经过境外 Matrix 服务器（`matrix.rainzt.cn` 是听雨的机器）。这是互联的固有属性，  
> 不是设计缺陷，但你得知道这件事、并且接受它。

### 明确不做

| 不做            | 理由                  |
| ------------- | ------------------- |
| 自建 homeserver | 一套 IM 后端的运维成本超过站点本身 |
| 自建联邦协议        | 没有生态，等于一个人的联邦       |
| 多房间 / 私聊      | 个人站没这需求，反而要处理权限     |
| 语音 / 视频       | 存储转码带宽全翻倍           |
| 已读名单          | 群聊级功能，在个人站只会变成社交压力  |
| 消息编辑          | 有撤回够了               |
| 端到端加密         | 服务端要审核，加密和审核天然冲突    |
| 表情回应跨站        | v1 只同步文字，减少兼容面      |

## 十、坑

1. **nginx 限流** — 轮询 0.4r/s 打不到 `api` zone（10r/s burst 20）。但别把聊天接口塞进  
   `admin_login` 那种 12r/m 档，那是 2026-11-18 的教训（一页并发 → 429 → fail2ban → 全站 DROP）。
2. **SQLite 保留字** — `AS to` 会静默返回全 0。新表别用 `to` / `from` / `order` 当别名。
3. **图片不进库** — 放 `/data/qingwu/chat-img/` + nginx `alias`。**别放 `public/`**，构建会清。
4. **`hold` 转 visible 要能被别人拉到** — 光靠 `WHERE id > ?` 会永久错过（id 早涨过去了）。  
   额外查「最近 60 秒从 pending 转 visible 的」。
5. **`recalled` 必须推** — 否则别人屏幕上的撤回消息摘不掉。
6. **先收红删后收原文** — `chat_redactions` 兜住，否则断线重连会让消息复活。
7. **`/sync` 游标只在入库后推进** — 先推游标再入库，中途崩了这条消息就永远丢了。
8. **workerd 重启** — `qingwu-api.service` restart 时轮询断 2~3 秒，前端静默重试，别弹错误。
9. **观感** — 别做成 IM 那种冷蓝灰。暖色系 + 爱弥斯，气泡浅暖底 + 细边，不是纯白卡片。

## 十三、v1 实现备注（2026-11-24）

v1 已落地在分支 `feat/changting`，commit `de297cf`。**和方案有四处偏差**，都记在这里，
免得以后看文档和代码对不上。

### 13.1 加了 `updated_at` 列（方案里没有）

方案 §8 说「hold 转 visible 后要额外查一次」，但没说靠什么查。
实现时发现必须有一个「状态最后变更时间」：光靠 `id > 游标` 永远拉不到那条
（id 早在游标之前就生成了）。所以 `chat_messages` 多一列 `updated_at`，
每次状态变更都写它，poll 查 `updated_at > now - 30s` 的那批。

同一列顺手解决了撤回的下发：转 `recalled` 的 id 从同一个查询里捞出来，塞进 `recalled`。

### 13.2 加了 `chat_rule_stats` 表（方案说要观测，没给表）

审核清单 §6 强调「每条规则要记命中数和误伤数」，但不落到表上就只是口号。
v1 先把表建了，`send` 时用 `waitUntil` 累加 `hits`；`hurt` 等后台页做出来再填。

### 13.3 多了一个 60 秒兜底放行

方案说「judge 挂了 → 放行」，但 `waitUntil` **不保证执行**（worker 重启、
机器重启、超时被掐）。那样会留下一条只有发送者自己永久可见的孤儿消息。

所以 `poll` 里顺手加了一条：`status='pending' AND ts < now-60s` → 转 visible。
机会式清理，不额外起定时任务。

### 13.4 三处前端顺带改动

| 文件 | 改了什么 | 为什么 |
|---|---|---|
| `EmojiPicker.tsx` | 加 `placement?: 'bottom' \| 'top'` | 长亭输入区在页面底部，向下弹会被容器 `overflow: hidden` 裁掉；左对齐还会顶出卡片右缘（312px 宽）。默认值没改，其余调用点零感知 |

### 13.7 一个踩到的坑（记给 v2）

写预览截图脚本时，未登录页面和登录页面共用同一个浏览器实例的 cookie store，
但 UA 不同 —— 撞上本项目「会话绑定 UA」的安全设计，服务端判定异常后**直接删了会话**，
表现是「截图跑到一半突然变成未登录」。以后任何自动化脚本都要用独立 browser context。
