# 方案 · 长亭（聊天室）

> 目标：给 [www.qingwu.ink](http://www.qingwu.ink) 加一个「有人在场」的聊天室，**并且和友站的聊天室联通**。  
> 名字：**长亭**（十里一长亭，供行人歇脚、相遇。每个人从不同的路上来，在这里碰面）。  
> 参考对象：听雨茶室（rainzt.cn/chat）。

---

## 一、参考对象拆解（这次结论改了）

第一版方案我判断「不做互联」，那是错的 —— 你要的就是互联。重新拆一遍：

| 他们的做法                | 判断                          |
| -------------------- | --------------------------- |
| 独立 `/chat/` 页面，留言页保留 | ✅ 学。留言是「一次性招呼」，聊天是「在场」      |
| 2 分钟撤回 + 留一行提示       | ✅ 学。成本极低                    |
| 「上次看到这里」未读分隔         | ✅ 学。一条 read 游标              |
| 消息轻回应                | ✅ 学，直接用你的表情包，不另做小猫          |
| @ 提及 + 邮件/浏览器通知      | ✅ 学。`mail.ts` 现成            |
| 草稿保存 + 失败重试          | ✅ 学。纯前端                     |
| Markdown 小文章         | ✅ 学。`richText.ts` 现成        |
| AI 24 小时巡查           | ✅ 学。`moderateComment` 现成    |
| 免登录填邮箱昵称             | ⚠️ 不学。你有 `accounts`，登录即进更干净 |
| 已读名单                 | ❌ 不做。群聊级功能，个人站里只会变成社交压力     |
| **Matrix 大厅 + 桥接**   | ✅ **要做，但走「接入已有大厅」而不是「自建」**  |

## 二、互联：三条路，只有一条划算

这是整份方案里唯一需要你亲自做决定的地方，因为另外两条的成本差一个数量级。

### 路径 A · 接入听雨的 Matrix 大厅（推荐）

现状：听雨已经在跑一个公开大厅 `#lobby:detached.online`，homeserver 是 `matrix.rainzt.cn`，  
里面已经有 **四个站**：听雨茶室、雪宝的站点（daily.yybb.us）、冷汐的杂货铺（lengxiqwq.com）、Somoe。

你只需要一个**共享转发账号**——听雨文档里明说「可以免费提供一个指定用于本站互联的 Matrix 转发账号，  
并为它登记站点来源」。拿到之后：

- 出站：`PUT /_matrix/client/v3/rooms/{roomId}/send/m.room.message/{txnId}`
- 入站：`GET /_matrix/client/v3/sync?since=<游标>`
- 你的机器上**不需要跑任何新服务**，只有一个 HTTP 客户端

**代价**：所有清吾茶友共用同一个 Matrix 身份，发言人靠消息正文里的元数据区分；  
消息会经过听雨的 homeserver（他能看到，也会做巡查）。

### 路径 B · 自建 homeserver，每人一个真 Matrix 账号

装 Synapse 或 Conduit，每个人有 `@xxx:matrix.qingwu.ink`。身份最干净，还能用任意 Matrix 客户端登录。

**代价**（这是劝退点）：

- 香港机多一个常驻服务，内存起步 1G+，还要 Postgres
- 联邦要开 8448 端口 + TLS + DNS SRV 记录，`fail2ban` 和限流规则要重做一遍
- 一个个人博客为聊天室养一套 IM 后端，运维成本超过站点本身

> **除非你打算把聊天室做成一个正经产品，否则不值得。**

### 路径 C · 自建轻量协议（站对站直接对接）

每站一个 `POST /chat/federate` + HMAC 签名。技术上最简单、最可控。

**代价**：没有生态。听雨、雪宝、冷汐都在 Matrix 上，你要么说服他们为你的协议改造，要么自己玩。  
**等于建一个只有自己一个成员的联邦**。

### 结论

**走 A。** 互联的价值在「有人」，不在「技术纯洁」。四个站已经在大厅里，你去就有话说；  
自己建一套再拉人，路径长十倍。

一个前置事实：**你得先有一个 Matrix 账号（或邮箱）去联系听雨申请**。这一步是人和人的事，代码替不了。

## 三、架构：本地优先，Matrix 是「另一个出口」

这是最重要的设计判断。三种做法：

| 做法               | 问题                                                          |
| ---------------- | ----------------------------------------------------------- |
| Matrix 当主库，本地只渲染 | Matrix 一挂，你连自己的聊天记录都看不到；历史要靠 `/sync` 慢慢拉；审核/搜索/撤回全要绕 Matrix |
| **本地当主库 + 桥接转发** | ✅ 采用                                                        |
| 双主（同时写两边）        | 一致性最难，撤回和删除要处理两套                                            |

**本地 SQLite 是唯一事实来源。** Matrix 挂了、token 失效、联邦断连——聊天室照常能聊，只是暂时不互联。

```
          ┌─────────────── 浏览器 /chat/ ───────────────┐
          │  每 2.5s GET /api/chat/poll?after=<id>      │
          └──────────────────┬──────────────────────────┘
                             │ nginx /api/ → :8787
                             ▼
                    worker/src/chat/*
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
            SQLite（主库）        chat_outbox（出站队列）
                  ▲                     │
                  │                     ▼
            chat_sync（游标）    Matrix C-S API
                  │                     │
                  └─────────────────────┘
                       桥接循环（cron，10s）
```

### 3.1 传输：轮询 2.5s，不用 WebSocket

理由不变：生产是 `wrangler dev --local` 常驻（`qingwu-api.service`），  
一 restart 所有 WS 连接同时断；轮询只是静默重试一次。

接口按**增量**设计（`after=id`），将来换 SSE/WS 只换传输层，消息格式不动。

### 3.2 桥接循环跑在哪

workerd 没有常驻循环。两个选择：

- **cron 服务**（推荐）：`qingwu-chat-bridge.timer`，每 10 秒跑一次同步脚本
- **poll 顺手推**：有人开页面时顺带同步一步。没人看页面时不同步，跨站消息会滞后

**推荐：cron 为主（10s），poll 只读本地库不碰网络。** 职责清楚，排障简单。  
代价是跨站消息最多慢 10 秒——对「不同站的两个人聊天」这个场景完全够。

> 如果以后觉得慢，再加「poll 顺手推」作为加速：用 `chat_sync.lock_until` 抢锁防并发，  
> 逻辑不用改，只是多一个触发点。

## 四、数据模型（9 张表，`0026_chat.sql`）

```sql
-- 消息。单一大厅，不设房间
CREATE TABLE chat_messages (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id    INTEGER,                    -- 本地消息才有；远程为 NULL
  body          TEXT    NOT NULL,           -- 原文（Markdown 子集 + 表情 token）
  kind          TEXT    NOT NULL DEFAULT 'text',   -- text | image
  reply_to_id   INTEGER,
  mentions      TEXT,                       -- JSON：[3,7] = 本地账号 id
  status        TEXT    NOT NULL DEFAULT 'visible', -- visible|pending|spam|deleted|recalled
  ts            INTEGER NOT NULL,
  ip_hash       TEXT,

  -- 互联（v2）
  origin        TEXT    NOT NULL DEFAULT 'local',  -- local | remote
  remote_sender TEXT,                       -- 完整 Matrix 用户 ID
  remote_nick   TEXT,                       -- 对方昵称（显示用）
  remote_avatar TEXT,
  remote_site   TEXT,                       -- 「冷汐的杂货铺」，前端挂「来自 XX」
  matrix_event_id TEXT,                     -- 去重 + 撤回映射
  matrix_txn_id   TEXT
);
CREATE INDEX idx_chat_id    ON chat_messages(id DESC);
CREATE INDEX idx_chat_acc   ON chat_messages(account_id, ts DESC);
-- matrix_event_id 唯一：重连补拉时挡住重复导入（NULL 不参与，本地消息不受影响）
CREATE UNIQUE INDEX idx_chat_evt ON chat_messages(matrix_event_id) WHERE matrix_event_id IS NOT NULL;

CREATE TABLE chat_reactions (
  message_id INTEGER NOT NULL, account_id INTEGER NOT NULL,
  emoji TEXT NOT NULL, ts INTEGER NOT NULL,
  PRIMARY KEY (message_id, account_id, emoji)
);

CREATE TABLE chat_reads (
  account_id INTEGER PRIMARY KEY,
  last_read_id INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

CREATE TABLE chat_presence (
  account_id INTEGER PRIMARY KEY,
  last_seen  INTEGER NOT NULL              -- poll 顺手节流写（>20s 一次）
);

CREATE TABLE chat_bans (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  account_id INTEGER, ip_hash TEXT,
  until INTEGER, reason TEXT, created_at INTEGER NOT NULL
);

-- ——— 互联专用 ———
-- 出站队列。本地原创消息先落这里，桥接按 FIFO 发
CREATE TABLE chat_outbox (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  message_id  INTEGER NOT NULL,
  op          TEXT    NOT NULL DEFAULT 'send',  -- send | redact | react
  txn_id      TEXT    NOT NULL,                 -- 幂等键，重试沿用同一个
  status      TEXT    NOT NULL DEFAULT 'queued',-- queued|sending|done|failed
  tries       INTEGER NOT NULL DEFAULT 0,
  next_at     INTEGER NOT NULL DEFAULT 0,       -- 退避时间
  last_error  TEXT,
  created_at  INTEGER NOT NULL
);
CREATE INDEX idx_outbox_due ON chat_outbox(status, next_at);
CREATE UNIQUE INDEX idx_outbox_txn ON chat_outbox(txn_id);

-- 入站游标（一行）。lock_until 防并发同步
CREATE TABLE chat_sync (
  id         INTEGER PRIMARY KEY CHECK (id = 1),
  room_id    TEXT,
  since      TEXT,                          -- Matrix next_batch
  lock_until INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL
);

-- 已收红删。**防止「先收到撤回、后收到原文」时把消息补回来**
CREATE TABLE chat_redactions (
  event_id   TEXT PRIMARY KEY,              -- 被撤回的 Matrix 事件 ID
  ts         INTEGER NOT NULL
);

-- 桥接日志（排障，只留 7 天）
CREATE TABLE chat_bridge_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL, level TEXT, msg TEXT
);
```

> **`chat_redactions` 这张表看着多余，其实是文档里特意点出的坑**：  
> 「先收到红删也要记住它，避免重连后把原文补回来」。没有它，一次断线重连就会让被撤回的消息复活。

消息永不物理删除（`status` 软删），和评论一致。

## 五、接口

| 方法   | 路径                                   | 说明                              |
| ---- | ------------------------------------ | ------------------------------- |
| GET  | `/chat/history?before=<id>&limit=50` | 首屏 / 向上翻页                       |
| GET  | `/chat/poll?after=<id>`              | 增量 + 在线人数 + `recalled:[id]`     |
| POST | `/chat/send`                         | `{ body, replyTo?, mentions? }` |
| POST | `/chat/:id/recall`                   | 2 分钟内、只能自己的                     |
| POST | `/chat/:id/react`                    | 再点一次取消                          |
| POST | `/chat/read`                         | `{ lastId }` 更新游标               |
| GET  | `/chat/bridge-status`                | **公开只读**：桥接是否在线、待发队列长度          |
| POST | `/admin/chat/bridge/pause`           | 站长暂停本方转发（互联合规要求）                |

`poll` 响应：

```json
{
  "ok": true,
  "messages": [ ... ],
  "recalled": [12, 15],
  "online": 5,
  "bridge": { "connected": true, "pending": 3 }
}
```

> 两个容易漏的字段：`recalled`（不推它，别人屏幕上的撤回消息永远摘不掉）、  
> `bridge`（互联状态要能一眼看到，不然「为什么我发的消息对方没收到」会变成玄学）。

## 六、互联协议细节

### 6.1 发出去的消息长什么样

**双格式**。结构化字段给懂的实现，正文协议头给只认正文的：

```json
{
  "msgtype": "m.text",
  "body": "[ID:小明];[URL:https://www.qingwu.ink/avatar/x.webp]\n\n下午好，我从清吾过来。",
  "format": "org.matrix.custom.html",
  "formatted_body": "下午好，我从清吾过来。",
  "org.tea-room.bridge": {
    "version": 1,
    "site": "https://www.qingwu.ink",
    "actor": { "id": "qingwu-u12", "nick": "小明" },
    "text": "下午好，我从清吾过来。"
  }
}
```

三个要点：

- `actor.id` 用 `qingwu-u<accountId>`，**改名、换头像、重装都不影响身份**。  
  不要用昵称当键——听雨文档里明确说了那是旧协议的限制（同名会撞、改名产生新身份）。
- `body` 首行的协议头是兼容层，听雨兼容这种写法，且头像只能靠它带过去。  
  （v1 结构化字段目前只读 ID / 昵称 / 正文，头像要双方扩展，所以 HTTP 地址必须留在正文头上。）
- `site` 字段只是便于识别；**来源以接收端配置为准**，不要指望它被信任。

### 6.2 Matrix 显示名

听雨约定的格式是 `昵称 · 站点名`。清吾这边用：

```
小明 · 清吾
```

（例子：`朝朝听雨 · 听雨茶室`、`遇见 · 冷汐的杂货铺`、`雪中来客 · 雪宝的站点`）  
中间是间隔点 + 两侧半角空格。站点名用正式名，别用「长亭」——长亭是房间名，  
混进「XX · 长亭」会让别站的人以为又来了一家叫长亭的站。

### 6.3 收到的消息怎么落库

```
/sync 拿到 to_device / timeline 事件
  ├─ 忽略自己的回声（sender == 本方转发账号 且 actor.id 以 qingwu- 开头）
  ├─ m.room.message
  │    ├─ 优先读 org.tea-room.bridge v1（id / nick / text）
  │    ├─ 没有就读正文协议头 [ID:..];[URL:..]
  │    ├─ 都没有就按 Matrix 成员资料（display_name / avatar）
  │    └─ 落库 origin='remote'，matrix_event_id 唯一索引挡重复
  ├─ m.room.member → 更新成员名册（不建本地账号）
  ├─ m.room.redaction → 软删对应行 + 写 chat_redactions
  └─ 成功后推进 since（**入库之后**才推进）
```

### 6.4 双向映射表

| 本地动作      | Matrix 动作                                                  |
| --------- | ---------------------------------------------------------- |
| 发消息       | `PUT /rooms/{id}/send/m.room.message/{txnId}`，存 `event_id` |
| 撤回（2 分钟内） | `PUT /rooms/{id}/redact/{eventId}/{txnId}`                 |
| 收到别人的撤回   | 按 `matrix_event_id` 找行，软删                                  |
| 表情回应      | 暂不互联（v1 只同步文字，减少兼容面）                                       |

### 6.5 限流（听雨的硬要求）

听雨文档里把这条列为接入前提，原文要求：**每个发言身份限频 + 整站出站队列限额 + 文字图片都算 + 共享账号按原发言人分别计数 + 超限给明确等待提示 + 不许攒一堆再一次性发**。

所以：

| 层级            | 额度                                        | 超了怎么办             |
| ------------- | ----------------------------------------- | ----------------- |
| 单个茶友（本地）      | 间隔 ≥1.2s，≤15 条/分钟                         | 前端提示「慢一点」，服务端 429 |
| 单个茶友（出站）      | 同上，按 `account_id` 计                       | 这条留在队列里等          |
| 全站出站          | ≤30 条/分钟（保守）                              | 队列 FIFO 排队，不合并批量发 |
| Matrix 返回 429 | 按 `Retry-After` 退避，兼容旧字段 `retry_after_ms` | 逐步拉长间隔            |

### 6.6 失败模式

| 故障            | 表现         | 处理                                        |
| ------------- | ---------- | ----------------------------------------- |
| token 失效（403） | 出站全失败      | 标记 `bridge.connected=false`，后台红标，**本地照常** |
| 房间别名解析失败      | 一个事件都拉不到   | 暂停同步，后台显示「房间 ID 待核对」                      |
| 联邦断连（超时）      | `/sync` 卡住 | 指数退避，最长 5 分钟一次                            |
| 重复导入          | 同一条出现两次    | `matrix_event_id` 唯一索引挡住                  |
| 先收撤回后收原文      | 撤回的消息复活    | `chat_redactions` 表兜住                     |

## 八、审核：本地清单 + 异步后审

⚠️ 完整清单见 `docs/审核清单-聊天室.md`。

聊天不能同步审核（每条卡 200~350ms 没人愿意说话），所以分两道：本地清单常数时间过一遍，  
**不命中直接放行**，之后异步走 Jev。命中 → 按 `block` / `hold` / `flag` / `pass` 四种动作处置。

`hold` 是关键：疑似但可能误伤的消息落 `pending`，**自己看得见、别人看不见**，AI 判完通常一两秒转正，  
本人无感。直接拒绝会把新来的人赶走。

**互联场景要加一条**：本地 `hold` 的消息**不进 outbox**。等判定通过再入队，  
否则你会在别的站上留下一串撤回不掉的痕迹。

## 九、合规与边界

### 站点已备案，互联带来三件事

1. **必须提示同步范围**：输入框附近常驻一句「这里的公开消息会同步到 Matrix 及其他互联站点」。  
   听雨文档把这条列为接入验收项。
2. **站长必须能一键暂停转发**：`/admin/chat` 上一个开关，出站队列立刻停。  
   误转发、刷屏、账号被盗都用得上。
3. **他人撤回请求要能响应**：友站要求删掉某条跨站消息时，本地要有对应入口。

> 内容会经过境外 Matrix 服务器（`matrix.rainzt.cn` 是听雨的机器）。这是互联的固有属性，  
> 不是设计缺陷，但你得知道这件事、并且接受它。

### 明确不做

| 不做            | 理由                  |
| ------------- | ------------------- |
| 自建 homeserver | 一套 IM 后端的运维成本超过站点本身 |
| 自建联邦协议        | 没有生态，等于一个人的联邦       |
| 多房间 / 私聊      | 个人站没这需求，反而要处理权限     |
| 语音 / 视频       | 存储转码带宽全翻倍           |
| 已读名单          | 群聊级功能，在个人站只会变成社交压力  |
| 消息编辑          | 有撤回够了               |
| 端到端加密         | 服务端要审核，加密和审核天然冲突    |
| 表情回应跨站        | v1 只同步文字，减少兼容面      |

## 十、坑

1. **nginx 限流** — 轮询 0.4r/s 打不到 `api` zone（10r/s burst 20）。但别把聊天接口塞进  
   `admin_login` 那种 12r/m 档，那是 2026-11-18 的教训（一页并发 → 429 → fail2ban → 全站 DROP）。
2. **SQLite 保留字** — `AS to` 会静默返回全 0。新表别用 `to` / `from` / `order` 当别名。
3. **图片不进库** — 放 `/data/qingwu/chat-img/` + nginx `alias`。**别放 `public/`**，构建会清。
4. **`hold` 转 visible 要能被别人拉到** — 光靠 `WHERE id > ?` 会永久错过（id 早涨过去了）。  
   额外查「最近 60 秒从 pending 转 visible 的」。
5. **`recalled` 必须推** — 否则别人屏幕上的撤回消息摘不掉。
6. **先收红删后收原文** — `chat_redactions` 兜住，否则断线重连会让消息复活。
7. **`/sync` 游标只在入库后推进** — 先推游标再入库，中途崩了这条消息就永远丢了。
8. **workerd 重启** — `qingwu-api.service` restart 时轮询断 2~3 秒，前端静默重试，别弹错误。
9. **观感** — 别做成 IM 那种冷蓝灰。暖色系 + 爱弥斯，气泡浅暖底 + 细边，不是纯白卡片。

## 十三、v1 实现备注（2026-11-24）

v1 已落地在分支 `feat/changting`，commit `de297cf`。**和方案有四处偏差**，都记在这里，

### 13.1 加了 `updated_at` 列（方案里没有）

方案 §8 说「hold 转 visible 后要额外查一次」，但没说靠什么查。
实现时发现必须有一个「状态最后变更时间」：光靠 `id > 游标` 永远拉不到那条

每次状态变更都写它，poll 查 `updated_at > now - 30s` 的那批。

同一列顺手解决了撤回的下发：转 `recalled` 的 id 从同一个查询里捞出来，塞进 `recalled`。

### 13.2 加了 `chat_rule_stats` 表（方案说要观测，没给表）

### 13.3 多了一个 60 秒兜底放行

所以 `poll` 里顺手加了一条：`status='pending' AND ts < now-60s` → 转 visible。

## 十四、左侧栏（2026-11-24 补）

站长要求参考听雨茶室的侧栏，在聊天卡片**外面左边**加一栏。三块：我的卡 / 在线的人 / 长亭的话。

### 14.1 刻意不照抄的一处：没有 Lv.N 和 EXP

参考对象是「Lv.2 · 本级经验 61/63 EXP」。那是**副本面板**的语言，长亭是歇脚的地方。

换成：一个称呼 + 一条进度 + 一句「再聊 11 句就是「煮茶的人」了」。

阶梯只在 `worker/src/chat/who.ts` 的 `LADDER` 里定义一次：

```
0    初来避雨
5    檐下常客
20   煮茶的人
50   长亭故人
120  守亭的人
```

改档位只改这一处，前端只负责渲染。

### 14.2 三个设计判断

**① 撤回的发言也算数。** 计数口径是 `visible + pending + recalled`。
撤回是「说错了收回」，不是「没说」—— 按 visible 算会让爱撤回的人永远升不了称号，
而那不是在奖励什么好行为。`spam` / `deleted` 不算（那不是正常发言）。

**② 在线名单只取 `chat_presence`，不拿「最近发过言的人」凑数。**
发完就关页面的人不该还挂在名单上。窗口 5 分钟，和消息区那个「N 人在长亭」用同一个常数。

**③ 独立接口 `GET /chat/who`，30 秒一次，不跟 poll 的 2.5 秒。**
侧栏数据变化极慢（谁在线、我聊了几句），跟着轮询只会让每条消息的请求都多一次 JOIN。
`doSend` 成功后会主动刷一次（发言数要立刻变），其余靠 30 秒定时器。

### 14.3 一个时序坑

首屏 `init()` 里 `history` / `me` / `who` 是**并发**的，而 `chat_presence` 是在
第一次 poll 里才写的 —— `who` 跑在前面时表里还没有自己，出现「2 人在长亭，但只列出 1 个」。

修法：`who` 里先 `touchPresence(自己)`，再确保自己不在名单时 unshift 一条。
正在请求这个接口的人当然算在场。

### 14.4 窄屏

`grid-template-columns` 在 `max-width: 1023px` 折成单列，且**聊天优先**（`order` 换位）：
侧栏挪到聊天下面，而不是藏起来 —— 在线名单和公告在手机上一样有人想看，只是不该占首屏。

### 14.5 公告文案

写在 `ChatAside.tsx` 顶部的 `NOTICE` 常量里，不落库。
理由是它属于「内容」不是「状态」：公告是站长的口吻，跟着代码走；
谁在线、聊了几句这种状态才归数据库。（和友链「内容归仓库、状态归 D1」同一个原则。）

### 15.2 称号系统被否掉了（决策记录）

第一版做的「初来避雨 → 檐下常客 → 煮茶的人 → 长亭故人 → 守亭的人」+ 经验条，站长看过后说不要。

**这个判断是对的，记一下理由，免得以后有人又想加回来：**

称号是「进度」的语言。进度需要一个**终点**才有意义，而聊天室没有终点——没人是为了「升到守亭的人」才来聊天的。加上它之后，侧栏会变成一块「你还差 11 句」的计数器，把「来坐坐」变成「来打卡」。

删掉之后侧栏那个「我是谁」只剩头像和昵称，直接从会话里拿，服务端连数都不用算。`who.ts` 跟着瘦身成只回 `members`。

### 15.3 补的两个功能

**① 页签未读**

```
页面在后台时收到消息 → document.title = "(3) 长亭 · 清吾"
切回前台 → 清零并立刻补一次 poll
```

每次都「先剥掉旧前缀再加」，所以连续收到消息不会叠成 `(1) (2) 长亭`。

为什么值得做：长亭是「有人在场」的地方，但没人会一直盯着这一页。切去写文章、听音乐时，标题栏那个数字是唯一能把你叫回来的东西。十来行代码。

**② 表情回应**

八个固定表情：赞 / 喜欢 / 笑到了 / 哭了 / 围观 / 庆祝 / 好看 / 谢啦。

**为什么不做完整表情面板**：轻回应的意思是「不必回一句话，点一下就好」，挑一个比「从 153 个里选一个」快得多。要发表情进正文，输入框那边本来就有完整面板。

实现要点：
- `chat_reactions` 主键 `(message_id, account_id, emoji)`，再点一次就是删这一行
- 接口回**整份汇总**，前端直接替换 —— 自己加减的话，两个人同时点会出现「本地看着 2、实际是 3」
- 只为 `status = 'visible'` 的消息开放；撤回的、被拦的、删掉的一律不认
- `emoji` 只做形状校验 `^[a-z0-9_]{1,32}$`：服务端没有表情清单（在 `src/lib/emojis.ts`，属于前端资源），多存一个渲染不出来的 key 没有危害；真正要挡的是塞 HTML / 超长串

### 15.4 一个真 bug：0026 漏建了表

补表情回应时接口报 `no such table: chat_reactions` —— 方案文档 §4 明明写了九张表，
但写 `0026_chat.sql` 时只落了消息 / 游标 / 在线 / 封禁 / 规则统计那一串，**漏了这张**。

### 16.2 五个功能

**引用回复**：`reply_to_id` 0026 就留好了。被引用的那条只下发 **60 字摘要** ——
全文会让一屏消息的响应体膨胀几倍，而引用条本来就只需要「谁说了什么开头」。

**@ 提及**：输入 `@` 弹在线名单，选中后把「@打了一半的名字」整段替换成「@名字 」，
**并把光标落到后面**（不这么做光标会跳回开头，接着打字全插到最前面）。
`mentions` 存 id 数组，渲染时对「@了我」的那条挂小标。

**搜索**：`GET /chat/search?q=`。两个坑：
- LIKE 的 `%` 和 `_` 必须转义，否则用户输一个 `_` 就等于查全部

**正在输入**：`chat_presence` 加 `typing_at`（0028），前端 3 秒最多报一次，后端 6 秒窗口判定。
三个点**不做闪烁动画** —— 这是个持续状态，为三个点常驻跑 CSS 动画不划算。

> 不需要新开一路，poll 本来就每 2.5 秒跑一次，多带两个字段而已。记一笔。

> 而且**就算有绑定也用不了**：生产是 `wrangler dev --local`，
> R2 绑定会被模拟成本地目录，图根本到不了云端。

**现在的存储策略：优先 R2（S3 API + SigV4），没凭据才回退 SQLite。**

| | 走 R2 | 回退 SQLite |
|---|---|---|
| 触发条件 | `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` 三个都配了 | 缺任意一个 |
| 地址 | `https://img.qingwu.ink/chat/<时间戳>-<随机>.<ext>`（走 CF CDN，不经过 worker） | `/api/chat/media/:id`（worker 现吐） |
| 图片上限 | 4 MB | 1 MB |
| 视频上限 | 32 MB | 5 MB |
| 本地开发 | 不需要配 | 默认就是这个 |

- `chat_media` 加了 `url` 列：非空 = 在 R2，空 = 老数据还在库里
- 消息只存 `media_id`，前端拿 `mediaSrc()` 取地址（优先 url，兜底 worker）
- **为什么不把二进制塞进消息**：一条图片消息在 poll 里每 2.5 秒重发一次，
  几十 KB 的 base64 会让轮询流量翻十倍

**为什么不用 `[[r2_buckets]]` 绑定**：
生产跑的是 `wrangler dev --local`，那种绑定会被 miniflare 模拟成本地目录 ——
图写到本地文件夹里，别处根本访问不到。所以直接走 R2 的 S3 API，
纯 `fetch` + Web Crypto 手写 SigV4（约 100 行，不引 SDK）。

**怎么配**（服务器上）：
```bash
# 凭据在 /etc/qingwu-r2.conf（账号级，和备份脚本共用）
# 取 R2_ACCOUNT_ID / R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY
# 写进 worker/.dev.vars：
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
# 可选，以下是默认值：
# R2_BUCKET=qingwu-uploads
# R2_PUBLIC_BASE=https://img.qingwu.ink
# 然后 systemctl restart qingwu-api
```
**怎么验证配好了**：传一张图，接口回 `"stored": "r2"` 且 `media.url` 是
`https://img.qingwu.ink/chat/...`；如果是 `"sqlite"` 说明某个凭据没读到。

**只在假凭据下验证过什么**：签名路径能跑通、R2 失败会自动回退存库、日志有错误记录。
**没验证签名本身对不对** —— 那需要真凭据，只能在服务器上确认。

**上传链路**：
- 前端 canvas 压到长边 1600 / webp，循环降质到 ≤900KB
- **GIF 不压**：canvas 只取第一帧，压完动画就没了。原样传（限 1MB）
- 三种入口：选文件 / `Ctrl+V` 粘贴（截图最常用） / 拖进聊天区
- 服务端再验一遍 mime 与大小 —— 客户端的限制永远可绕过
- 只接受白名单 mime；从库里吐出去的响应带 `CSP: default-src 'none'; sandbox` + `nosniff`

**踩到的坑（记下来，别再犯）**：

> `data` 列原本按 BLOB 写。实测在这套「miniflare D1 + 本地 SQLite」里，
> bind 一个 `Uint8Array` 会被序列化成 `137,80,78,71,...` 这种**十进制字符串**，
> 读回来 `new Response()` 就是 198 字节的垃圾，不是 PNG。
> 改成存 base64 文本，两边行为一致（体积 +33% 换个可靠）。
> 验证方式：`cmp` 下载回来的字节和原文件，一致才算过。

### 16.4 一条该升级成纪律的教训

`0027` 补 `chat_reactions`、`0030` 补 `image_id` —— **同一个失误犯了两次**：
方案文档的表结构里写了，写 SQL 时漏了。两次都要等到第一次用那个字段/表时才炸。

> **纪律：迁移文件写完，逐项对一遍文档里的表名和字段名。**
> 建表/建列语句漏一条不会报错，而「文档有、SQL 没有」这种偏差，
> 靠读代码是发现不了的 —— 只有真跑到那一步才知道。

## 十七、这些功能在 Matrix 上怎么映射（v2 备查）

功能一路加到现在，桥接要处理的东西比最初方案写的时候多得多。
**趁还记得，把每一项对应的 Matrix 事件/字段列清楚** —— 等真接的时候（要等听雨发账号），
不用再回头翻一遍 Matrix 规范。

| 长亭的功能 | Matrix 侧怎么写 | 麻烦在哪 |
|---|---|---|
| 纯文字 | `m.room.message` + `msgtype: m.text` | 结构化的 `org.tea-room.bridge` 放 ID/昵称/正文，`body` 首行仍是 `[ID:..];[URL:..]` 协议头 |
| Markdown / 表情 token | `format: org.matrix.custom.html` + `formatted_body` | 我们的 `richText` 只输出白名单标签（strong/a/code/pre/p/ul/ol/blockquote），转 HTML 时直接复用，别放开标签 |
| 行内表情 `:[key]` | `formatted_body` 里带 `data-mx-emoticon` 的 `<img>` | **别站没有我们的表情素材**。转发前要把表情上传到 Matrix 媒体仓库换成 `mxc://`，否则对面是破图 |
| 图片 | `msgtype: m.image` + `url: mxc://…` + `info{w,h,mimetype,size}` | 我们存的是库里的 base64；入站要下载 mxc 再转存 `chat_media`，出站要反向上传。**这一项工作量最大** |
| 视频 | `msgtype: m.video`（或 `m.file`） | 我们上限 5MB，Matrix 媒体仓库单文件上限可能更小，超了要降级成链接 |
| 引用回复 | `m.relates_to.m.in_reply_to.event_id` | 必须维护双向映射：本地 `reply_to_id` ↔ Matrix `event_id`。对不上的引用**保留可读文本**，不要丢 |
| @ 提及 | `m.mentions.user_ids` | 我们存本地 `account_id`，要映射成 Matrix 用户 ID。**共享转发账号下这条路走不通**（所有人同一个 ID），只能退化成正文字符 `@昵称` |
| 撤回 | `m.room.redaction` 事件 | 本地 `status='recalled'` ↔ redaction；`chat_redactions` 表已经为「先收到撤回、后收到原文」准备好了 |
| 表情回应 | `m.reaction` 事件 | **v2 暂不同步**。要做的话本地 `chat_reactions` 的主键正好够映射 |
| 已读 | `m.read` 回执（`m.receipt`） | 本地 `chat_reads` 游标 ↔ 回执。**共享账号只能表示「这个账号读过了」**，代表不了具体是谁 |
| 正在输入 | `m.typing` 临时事件 | 本地 6 秒窗口 ↔ Matrix 的 typing timeout。共享账号同样区分不出人 |
| 搜索 | 不用同步 | 各站搜各站的本地副本就行，跨站搜索没有产品价值 |

### 三个必须提前想清楚的点

**① 媒体是最大的坑。** 文字、引用、撤回都有现成字段，而图片要走 Matrix 内容仓库：
出站要上传换 `mxc://`，入站要下载 mxc 转存本地。双向都要处理失败（媒体过期、
对面 homeserver 挂了），失败了就降级成「一张图（加载失败）」，不能让整条消息丢。

**② 共享转发账号会削掉一半的「社交功能」。** 听雨给的那种账号，所有清吾茶友共用一个
Matrix 身份 —— 于是 `@` 提及和已读回执都只能表示「清吾有人读过了」，分不出具体是谁。
如果这两件事对体验很重要，唯一的解法是自建 homeserver 给每人分配虚拟账号（见 §二 路径 B）。
**这是 v2 开工前要重新确认一次的取舍。**

**③ 出站队列要能表达「这条永远发不出去」。** 现在 `chat_outbox` 只有 queued/sending/done/failed。
接入后会出现「媒体超限」「房间权限不足」这类**不可重试**的失败，
得区分出来，否则队列会一直重试到天荒地老。

## 十八、操作条为什么「点不到」：尺寸、位置与 hover 死带（2026-11-24）

站长连续两轮反馈「很难按到」。第一次我以为是缝隙，把 `calc(100% + 0.15rem)` 改成
`top: 100%`，用 24 步轨迹验证「消失 0 次」——**但问题没解决**。第二次才查清：
那不是缝隙问题，是**三个缺陷叠在一起**。

### 18.1 规范怎么说

| 来源 | 要求 |
|---|---|
| WCAG 2.2 **SC 2.5.8**（AA，新增） | 指针目标 **≥ 24×24 CSS px**；不足则相邻目标之间要留出足够偏移 |
| WCAG 2.2 **SC 2.5.5**（AAA） | **≥ 44×44** |
| Apple HIG | 44×44 pt |
| Material | 48×48 dp |
| Fitts 定律 | 视觉尺寸和命中区可以不一致 —— 可以只放大命中区；贴边、整行的目标近乎「无限大」 |

改造前实测：`回复` 高 **18px**、`+` 只有 **21.6px** —— 两个都不达 AA 底线。

### 18.2 Slack 自己的结论

Slack 做「简化布局模式」时的原话（面向眼动仪 / 头控用户）：

> Hover-only menus add another layer of difficulty. They require precise movement
> and **can disappear before someone has time to act**.

他们的解法是两条：**最小 40×40 目标**，以及**动作不再依赖 hover**（挪进常驻菜单）。
Slack / Discord / Element 的消息操作条位置也一致：**贴着消息本身、在同一水平带上**
（右上角或右侧），不是浮在消息下方的独立窄条。

### 18.3 三个缺陷与改法

**① 尺寸不达标** → `回复/撤回` 做成 30×30 的浅色小按钮（原来 18px 高的裸文字），
`+` 也是 30×30，间距 5px。

**② 操作条在行盒子之外** → 原来绝对定位在气泡**下方**，而行的盒子只包住气泡，
于是「想点按钮」必须先离开这一行。从下往上够会先命中**下一行**、露出的是下一行的按钮；
从上往下够，偏出那条 18px 窄带就掉 hover。现在挪到气泡**右侧同一水平带**
（自己的消息镜像到左侧），整个按钮落在行盒子内部，进出都不会断 hover 链，
滑过去还是一次纯水平直线。

**③ 行与行之间的 margin 是 hover 死带** → `margin-top: 0.85rem` 不属于任何元素盒子，
鼠标落在这条缝里没有任何行处于 `:hover`，按钮凭空消失。改成 **`padding-top`**，
行盒子首尾相接，纵向连续。（Slack / Discord 的消息行也是整块无缝的。）

### 18.4 验收数据

用真实鼠标轨迹 + `elementFromPoint` 逐点采样（1440 宽，指针从聊天区右下角
斜着往上摸到按钮）：

| 指标 | 结果 |
|---|---|
| 按钮尺寸 | 回复 41×30、`+` 30×30（≥24×24 ✓） |
| 操作条是否完全落在所属行盒子里（纵向 + 横向） | 是 |
| 路径上「指针在某行上、但这一行的按钮不可见」 | **0 / 41 步** |
| 从四个方向（左/右/上/下）逼近到按钮中心 | 末端全部 `pointsToButton: true` |
| 表情弹层是否被裁 | 否（240×39，未触边） |

### 18.5 窄屏与触屏是另一套布局

侧放需要气泡右侧有地方。实测 **390px 宽 + 鼠标** 时，绝对定位会把滚动容器
撑出 **37px 横向溢出**（气泡最宽 70%，右边只剩几十像素）→ 聊天区永久多一条横向滚动条。

所以 `@media (max-width: 640px), (hover: none)` 统一切成**气泡下方 + 正常流**：
- 进流而不是继续绝对定位：绝对定位在下方会和下一行文字叠在一起
- 「提前预留的 35px」反而成了优点 —— 这块空白属于行盒子内部，悬停它同样算悬停行，
  显隐依然可靠，而布局不会因为 hover 跳动
- 触屏（`hover: none`）上直接**常显**，没有 hover 可用就不该藏

实测 390 / 420 / 560 / 641 / 700 / 768 / 1024 / 1280 / 1440 九个宽度：
横向溢出 **0**，操作条 **没有**越出容器。

### 18.6 记一条通用教训

**「悬停才出现的浮层」只要和触发元素不在同一个盒子内部，就一定有死区或错行。**
判断方法不是看像素缝隙，而是问：*鼠标从 A 走到 B 的整条路径，是否始终落在
「让浮层可见」的那个元素内部？* 不是的话，改结构（同盒、整行触发、或进正常流），
光调 `top` 是调不好的。

## 二十、懒加载 / 虚拟滚动 / 缓存：要不要做（2026-11-24 评估）

先摆数据（本地实测，不是估的）：

| 指标 | 实测值 |
|---|---|
| 首屏 `GET /chat/history?limit=30` | **6.9 KB**（20 条；约 **348 B/条**，含表情/引用/媒体元信息，不含二进制） |
| 空转一次 `GET /chat/poll` | **117 B**（2.5 秒一次 ≈ 2.8 KB/分钟） |
| DOM 规模 | 245 个节点 / 16 行 ≈ **15 节点/行** |
| 媒体二进制 | 走 R2 + `cache-control: immutable, 1y`，由 CDN 直出，不进轮询 |

### 20.1 虚拟滚动：不做

15 节点/行，1000 条才 1.5 万节点 —— 到那一步浏览器才开始明显掉帧，而长亭现在一共 20 条。
真要撑长，正确做法是**窗口化**而不是虚拟滚动：

- 窗口化：DOM 里只保留最近 N 条（比如 300），更早的整段丢弃，顶部留一个「看看更早的」锚点。
- 虚拟滚动的问题在**行高不定**：一条消息可能带图片、视频、引用、回应条，
  高度得靠 `ResizeObserver` 逐条补偿，补偿晚一帧就跳一下。
  我们的消息形态刚好是最不适合虚拟滚动的那种。
- 结论：等单次会话真的上千条再说，方案优先选窗口化。

### 20.2 懒加载：基本已经有了

- 图片 `loading="lazy"`、视频 `preload="metadata"`；
- 媒体二进制带一年 immutable 缓存，同一条消息在轮询里只传 `media.id`；
- 翻页是「看看更早的」按钮（不是滚动触发）。

**唯一可做的是「滚到顶部自动加载」，但我倾向不做**：聊天里往上翻历史时，
新内容会插在顶部把正在看的位置顶下去 —— 必须精确锚定 `scrollHeight` 差值才不会跳，
收益（省一次点击）小于风险（翻历史时画面抖）。

### 20.3 缓存：只做了「首屏快照」（已实现）

现状：`ClientRouter` 开着，但 `ChatRoom` 是 `client:only` 岛 —— 每次从别的页回到 `/chat/`
都会**重建整个岛**，重新拉 30 条 + 重算 who，中间是一段白屏。

做法（`ChatRoom.tsx` 顶部 `SNAP_KEY` 那一段）：
- `sessionStorage` 存 `{ v, at, accountId, hasMore, lastId, lastRead, messages }`，TTL 90 秒、最多 30 条（约 6.5 KB）；
- 进页面先按快照铺满（`loading` 初值就是 `!boot`，没有骨架屏），同时照常请求 `history`；
- 请求回来**整份替换**而不是合并 —— 撤回、审核状态、已读线都由这次替换校正；
- `init({ quiet: true })` 是「悄悄校正」，它**不会**把 `failed` 切成整屏错误页，
  只在顶部留一行「这会儿没连上，先给你看上次的内容」；
- 收到新消息 / 自己发完，3 秒节流地重写快照 —— 否则会出现「刚收到的话切页回来先消失」；
- 边界写死在注释里：sessionStorage 是本标签页的，关掉就没了；**不做**跨会话历史缓存；
  它只加速渲染，不改任何数据来源。

实测（localhost，三轮取中位数；`/chat/` → `/` → 点导航回来，ClientRouter 重建岛）：

| | 首行消息出现 |
|---|---|
| 无快照 | **260 ms** |
| 有快照 | **168 ms** |
| 差 | **−92 ms** |

localhost 上 API 延迟约等于 0，所以这 92ms 全是「省掉一次等请求 + 渲染」。
线上（香港机 + nginx 代理，往返约 100ms 起）收益会随之放大：快照是在**任何请求返回之前**
就把内容画出来的。

风险（已接受并写进实现）：同一标签页里换人登录，最多 300ms 内会看到上一个人留下的内容，
随后被整份替换。快照里存了 `accountId`，但真正的保险是「替换永远覆盖全量」。

## 二十一、视觉精修（2026-11-24 夜 · 用 finesse 的 redesign 流程）

按 finesse 的 `redesign` 走：先审、再定保护项、按杠杆排序改，不动结构。

**保护项（明确不改）**：配色与绯红强调色、页面骨架（页头 / 侧栏 / 会话 / 输入区）、
`.page-shell` 宽度、在线小圆点的「不呼吸」判断（以前明确写过「常驻闪的东西最耗神」）。

### 21.1 审出来的问题

| 类别 | 发现 |
|---|---|
| D 组件状态 | 加载态只有一行灰字，整张卡片空着；空态只有两行灰字且贴在卡片底部 |
| D 组件状态 | 拖文件进聊天区能发但**零反馈**，松手前不知道会发生什么 |
| A 排版 | 时间分隔是居中纯文字，读起来像正文里插了一句；时间/已读数字是比例字体，逐帧抖 |
| F 动效 | 新消息**完全没有入场**，一条消息凭空出现；也没写 reduced-motion 分支 |
| 交互 | 图片消息点开是 `window.open` 跳新标签页，离开了站内阅读上下文 |
| A11y | 会话区没有 `role="log"`，读屏不知道这是会滚动的记录；焦点环全靠浏览器默认 |
| 移动 | 输入区按钮 28px（低于 WCAG 2.5.8 之外的 44 建议值）；占位符在 390px 下折成两行 |

### 21.2 改了什么

1. **骨架屏**：5 行占位（左 / 右 / 左 / 右 / 左），按聊天的真实节奏摆；呼吸动画 1.8s、
   `prefers-reduced-motion` 下静止。实测高度 730px，正好铺满卡片，不再是一行字。
2. **空态**：一枚细线方框里的「亭」印章 + 「长亭还空着」+ 一句邀请；未登录时带「坐下聊聊」。
   外层 `.q-chat__scroll.is-empty` 把内容改为垂直居中（原来被 `margin-top: auto` 压到底部）。
3. **时间线**：两侧各一条 1px 细线，中间才是时间。
4. **等宽数字**：时间、已读、字数、游标线统一 `font-variant-numeric: tabular-nums`。
5. **新消息入场**：220ms `cubic-bezier(.22,.61,.36,1)` 上浮 5px。**只对「进来之后才到」的
   消息生效**（首屏与快照里的那批不动），reduced-motion 下关闭。
6. **图片改用站内灯箱**：给媒体容器加 `data-zoomable`，`ImageZoom` 的选择器从
   `.prose img` 扩到 `.prose img, [data-zoomable] img`，同组收集也认这个容器。
   点开停在本站，Esc 关，← → 翻同组。
7. **读屏**：会话区 `role="log" aria-live="polite" aria-relevant="additions"`；
   所有按钮/输入框/链接加 `:focus-visible` 绯红焦点环。
8. **拖拽投放态**：`dragenter` 计数器（不是布尔，嵌套元素的 enter/leave 会成对狂发），
   投放时整卡虚线覆盖 + 「松手就发出去」。
9. **触屏目标**：工具按钮 40px、发送 44px（`@media (hover: none)`）；390px 横向溢出 0。
10. **占位符缩短**为「说点什么… @ 叫人」：原来那句在 390px 下折两行，
    输入框一进页面就变高（实测 54px → 33px）。

### 21.3 刻意没做

- 气泡渐变 / 头像光晕 / 在线点呼吸 —— 前两条是 AI slop 的标准配置，第三条与既有判断冲突。
- 虚拟滚动、滚到顶自动加载 —— 理由见 §20。
- 侧栏「我的卡」加数据 —— 称号那套刚被否掉（§15.2），不要再换个名字加回来。

### 22.3 本轮补的三件事（其中一件是修 bug）

**① 桌面提醒（新）**
顶栏加「提醒」开关 → `Notification.requestPermission()`（必须用户手势，不能自动弹）
→ 只在 `document.visibilityState === 'hidden'` 时发通知；`tag: 'changting'` 让多条合并；
点通知回到页面并贴底。偏好存 `localStorage`，权限状态三态（off / on / denied），
被浏览器拒了会说「去地址栏左边放行」，而不是继续弹没用的窗。

**② 页签未读数（之前是死的）**
原实现只在 `visibilityState !== 'visible'` 时累加未读，而**轮询本身就只在可见时跑** ——
那个分支永远进不去，标题里的数字一次都没出现过。
修法：后台不再完全暂停，改成 10 秒一次（空转 117 字节 ≈ 42 KB/小时）。
这也顺带成了通知的触发源：没有后台轮询，就没有「新消息」可提醒。

**③ 断线提示（新）**
连续 2 次 poll 失败才亮「连接断了，正在重连…」，恢复自动收回；
另外监听 `window.online`，系统恢复联网时立刻补一次，不等 10 秒。

实测（puppeteer + 真发消息）：开提醒后切到后台，另一个账号发 2 条 →
桌面通知触发 2 次、标题变 `(2) 长亭 · 清吾`；切回前台标题归零、消息已就位；
CDP 断网 7 秒后提示条出现、恢复 4 秒后消失。

## 二十三、输入框「双框」：焦点环画错了层（2026-11-24）

站长截图：输入框聚焦时外面一圈绯红、里面还有一条发丝边。

**根因是两层各自画了一遍。** 上一轮我给所有交互元素加了
`.q-chat :is(button, textarea, a):focus-visible { outline: 2px solid …; outline-offset: 2px }`，
权重 (0,2,1) 盖过了 `.q-chat__input { outline: 0 }` —— 于是 textarea 自己画了一圈；
而外层 `.q-chat__inputwrap:focus-within` 又在改边框色。两个圆角、两个 inset 叠在一起，
看起来就像一个画错的相框。

**改法（和开源聊天客户端一致）**：焦点只画在**容器**上。

- `.q-chat .q-chat__input:focus-visible { outline: none }` —— 显式排除，权重 (0,3,0)
- 容器：`border-color` 提到 46% 绯红 + `box-shadow: 0 0 0 3px` 玫瑰色柔环
  （用 `box-shadow` 而不是 `outline`：不占布局，光标进出不会把下面内容顶动）
- 补了鼠标悬停的边框加深 —— 之前输入框完全没有 hover 反馈，像一张图
- 发送按钮补 hover（同色系混棕压暗，不混黑，混黑会把暖调压成脏红）+ 禁用时 `cursor: not-allowed`
- 两个工具按钮间距 0.25rem → 0.3rem（手机上点「表情」容易点到旁边那张图）

实测：聚焦时 textarea 计算样式 `outline: 3px none`，容器 `box-shadow` 与 `border-color` 均生效；
截图（3× 放大）确认只有一圈。

## 二十四、把清单上的四项做掉（2026-11-24 深夜）

依据 §22.4 的排序，这一轮实现前四项：**编辑已发 / 举报 / 置顶 / 任意文件**。
表与列全在 `0032_chat_compose.sql`（一份迁移，四条一起走）。

### 24.1 编辑已发

- `chat_messages` 加 `edited_at`（毫秒）。有值 = 前端显示「已编辑」
- `POST /chat/:id/edit { body }`：
  · 只认本人（按 `account_id`，不按昵称）
  · **5 分钟窗口**，和前端按钮的显示条件用同一个数字（不一致会出现「按钮在、点了报错」）
  · 改完**重新过一遍本地清单** `screen()` —— 不重审等于开了一个「先发干净的、5 分钟内改成广告」的后门
  · 命中的仍走异步 AI 复核（复用 `judgeLater`，`wasPending: false`，不把原消息降级）
  · `updated_at` 推到当前时间 → poll 的「30 秒内变更过」会把新正文补发给所有人，
    不需要刷新页面
- 前端复用输入区：点「编辑」→ 上方出现「正在改这条 · Enter 保存，Esc 取消」，
  发送按钮换成铅笔、`aria-label` 变「保存修改」，Enter 保存、Esc 放弃。
  不弹新框的理由：改一句话不该换一个界面，表情 / @ / 粘贴都在原位可用。

### 24.2 举报

- 表 `chat_reports(id, message_id, account_id, reason, status, ts)`，
  `UNIQUE(message_id, account_id)` —— 一人一条只能报一次
- `POST /chat/:id/report { reason }`，理由沿用审核的五类 + `other`；
  不能报自己的；每人每小时 20 条上限
- **只落库，不自动隐藏**。按举报数自动下架是最省事的攻击面：注册三个号就能让任何人的话消失。
  处置权留给站长（`/admin/chat` 那页做的时候直接读这张表）
- 前端：别人的消息操作条里多一个「举报」，弹层六个理由，回执会区分
  「交到站长那儿了」和「这条你已经报过了」

### 24.3 置顶

- 表 `chat_pins(room TEXT PRIMARY KEY, message_id, account_id, ts)`，
  主键钉死 `'main'` —— 一间房只有一个置顶位（两个公告等于没有公告）
- `POST /chat/pin { messageId }`：只有 `role='admin'` 能调；`messageId=0` 取消
- **poll 每次都带 `pin`**（约 100 字节），换来「站长一置顶，所有人两秒内看见」；
  没有它就只能等下次刷新
- 前端：会话区上方常驻一条，点它跳到那条（不在当前页就说「往上翻一翻」，
  不主动 loadMore —— 为一条旧消息把几十条历史拉进来会冲掉滚动位置）；
  站长右侧多一个 ×

### 24.4 任意文件

- `chat_media` 加 `filename`；`kind` 增加 `'file'`
- 白名单（**不是黑名单**）：pdf / zip / txt / md / csv / json / epub / docx / xlsx / pptx。
  刻意不收 `text/html` 与 `image/svg+xml` —— 这些字节会以原 `content-type` 从同源吐出去，
  一个塞了 script 的 svg 就是本站域名下的 XSS
- 上限 5MB（两条存储通道一致）
- 文件名清洗：去路径分隔符与控制字符（防响应头注入）、截 60 字符、扩展名按 mime 兜底
- 下载时加 `content-disposition: attachment`；文档一律「下载」，不在浏览器里开
- 前端：文件不放进气泡、也不挂灯箱，做成一张「图标 + 文件名 + 大小 + 下载」的卡片

### 24.5 验证

接口层（curl）：
- 编辑自己的 → `editedAt` 落库、历史里可见；改别人的 → 403；改 5 分钟前的 → 400
- 举报 → `already:false`；重复 → `already:true`；报自己 → 400 `self`；非法理由 → 400
- 访客置顶 → 403；站长置顶 → history 与 poll 都带 `pin`；取消 → `pin:null`
- 传 `text/plain` → `kind:file` + `filename`；`GET` 返回 `Content-Disposition: attachment` 且字节一致

界面层（puppeteer 真点击）：
- 悬停自己的消息 → 按钮组 `[回复, 编辑, 撤回, 置顶, +]`（站长还会多一个「置顶」）
- 点编辑 → 编辑条出现、草稿预填、按钮变「保存修改」、焦点在输入框
- 回车保存 → 正文更新、「已编辑」小标出现、草稿清空、提示「改好了」
- 别人的消息点举报 → 弹层六个理由，选一个后关闭并给出回执

### 24.6 这一轮没做的两项（有明确理由）

- **链接预览**：要在服务端抓外链 OG，必须做域名白名单 + 私网地址拦截 + 体积/超时上限，
  是一整块安全工程（SSRF 面），不是「顺手加个卡片」。
- **语音消息**：MediaRecorder 录音 → 上传 → 播放器 → 时长/波形，且要考虑 iOS Safari 的
  `audio/mp4` 兼容。估算各一天，价值取决于大家愿不愿意在博客底下说话。

## 二十五、impeccable 评审：修掉 10 处（2026-11-24 夜）

互不可见，最后由我合成。确定性扫描（`impeccable detect`）二进制下载失败，
所以「自动检测器」这一路缺席，浏览器证据那一半照常跑了。

### 25.1 修复前实测（1440×940）

| 指标 | 数值 |
|---|---|
| 文本对比度 | 160 个文本节点，**5 个不达标**（最小 4.34:1） |
| 命中区 <24px | 顶栏「提醒/搜索」**63.8×21.3**、表情回应小标 **37.6×21.5** |
| 横向溢出 | 641→**29.4px**、700→**17px**、728→2.4px、730→0（641–729 这一段漏网） |
| CLS | **0.188**（差），最大单次位移 **0.1826 @226ms**，源元素是 **footer（97%）** |
| Tab 顺序 | 92 步，其中 **55 步落在 opacity:0 的操作条上** |
| 手机输入框 | **14.4px** → iOS Safari 聚焦时自动放大整页 |
| 举报弹层 | Tab **8/8 步**跑到弹层外；关掉后焦点掉到 body |

### 25.2 改了什么

**① CLS 0.188 → 0.0012（降 99.4%）**
根因不是侧栏，是**岛还没水合时占位高度为 0**：`client:only` 服务端不产标记，
页脚先坐在上面，226ms 后聊天卡 732px 长出来把页脚推下去。
在 `chat/index.astro` 外面包一层 `.q-chat-slot`，用**和 `.q-chat` 完全相同的 clamp**
先占住高度。窄屏同理（那时页脚已在视口外，后续增长不计入 CLS）。

**② 对比度 5 处全清（0 失败 / 160 节点）**
- 时间线与时刻：`--color-subtle`(4.34/4.47) → `--color-muted`(≈6.2)，字号 0.68→0.75rem
- 昵称：棕色 #8b5a3c 落在粉色气泡上只有 **4.26:1** → 90% 墨 + 保留 500 字重
- 「已编辑」9.9px → 12px，`--color-accent-soft`（更暗一档的绯红）
- 顶栏按钮 11.2px → 12px
- `.q-chat__meta` 行整体提到 0.75rem

**③ 命中区：0 个 <24×24**
顶栏 63.8×21.3 → **28px 高**；表情回应小标 → **min-height 24px**；
触屏上操作按钮 → **36px**（拇指指腹约 42px，30px 高 + 5px 间距点错率高）。

**④ 641–729px 横向溢出清零**
断点从 640 提到 **768**。这一段的根因是「气泡 70% 上限 + 30px 按钮 + 间距」塞不进
滚动容器；730–1023 侧放本来是够的，所以没有跟着侧栏一起改成 1023
（那会让每条消息白多 35px 高）。14 档宽度实测溢出全部为 0。

**⑤ 触屏：69 个常显按钮 → 点一下展开，且互斥**
原来 `@media (hover: none)` 把操作条设成常显：23 条消息 = 69 个按钮平铺，
一屏 5 条消息压着 15 个按钮。改成默认收起、**点消息展开**（`click` 而非 pointerdown：
滚动结束浏览器不派发 click，划列表不会一路点开）。打开状态提到 ChatRoom 里，
同一时刻只有一条展开。

**⑥ 手机输入框 16px**
<16px 会触发 iOS Safari 聚焦自动缩放整页，且不会自己缩回来。断点 768。

**⑦ 键盘：滚动区可聚焦 + 弹层焦点契约**
- `.q-chat__scroll` 加 `tabIndex=0 / role=region / aria-label`，PageUp 实测滚动 918px
- 新增 `useDialogFocus()`：打开时焦点入弹层、Tab 内部循环、Esc 关闭、关闭后归位。
  举报弹层实测 **Tab 12 步 0 次逃逸**，Esc 关闭后焦点回到触发按钮
- 灯箱补焦点循环 + 关闭后归还（原来 Tab 会跑到背后页面）

**⑧ 浮层出口**
表情弹层原来只有「再点一次 +」能关；现在 Esc / 点外面都关。

**⑨ 加载态不再说假话**
登录用户的第一帧之前落进「还没进门 / 坐下聊聊」（170px），身份一到缩成 60px 的卡。
现在同高占位 + 快照里存 account，第一帧就是真卡。

**⑩ 细节**
时间线两侧细线 13%→22% 棕（417px 长的线肉眼看不见 = 没切开）；
「还没有人在」→「还没有人在长亭」；同一行不再出现两个相同时间（时间线已画过就省掉 meta 里的时刻）；
窄屏放开 `overscroll-behavior`（手指在聊天卡上划到底，要能继续划到侧栏）；
输入框光标与选区改用配色；触屏 36px 操作按钮。

### 25.4 第二轮：触屏入口的三种方案与最终做法

第一版把触屏操作条改成「常显」→ 23 条消息 69 个按钮；第二版改成
`@media (hover:none)` 下 `opacity: 0` → **仍占 36px 高**，23 条约 828px 空白带；
第三版改成 `display: none` → 不占位了，但**键盘用户从此进不去操作条**（可聚焦点 70 → 0）。
三次都不是「调参」，是结构选错。

最终做法（两个独立评审给出的方案里选 C）：

- **`.q-chat__actstoggle`**：气泡右上角外侧 6px 的一枚 28px 圆按钮（三个点）。
  平时 `opacity: 0` + `pointer-events: none`（手指点它时事件穿过去命中气泡，
  走整行 toggle，不会双触发）；**键盘聚焦或展开时现形**。
- 显隐用 `:focus` 而不是只 `:focus-visible`：实测触摸环境里 Tab 到它时
  `:focus-visible` 不命中，opacity 停在 0，等于给了一个看不见的焦点目标（2.4.7）。
- **`transition` 里不能带 `opacity`**：渐入会让「聚焦那一帧」有约 36ms 全透明，
  屏幕上看不出焦点在哪。显隐由键盘动作直接决定，不需要渐入。
- 可见态的边界要自己立起来：圆面 `#fffdfb` 对白 **1.00:1**、16% 发丝边 **1.25:1** ——
  视觉上等于不存在（WCAG 1.4.11 要 3:1）。聚焦/悬停时描边上实色绯红（≈5.4:1）+ 带偏移的柔和投影。
- **Esc 挂在整行**，不是挂在入口按钮上：焦点已经 Tab 进操作条（比如「回复」）时，
  只绑在入口上的话按 Esc 毫无反应。收起后焦点还给入口。
- 键盘 Enter 展开时，焦点**交接**给操作条第一个按钮，入口随即让位（`[aria-expanded=true]` 时 opacity 0）——
  否则 28px 的圆会啃掉 meta 行末尾，而那正是「这是谁说的」。
- **一次性提示**「轻点一条消息，可以回复、回应或举报」：只在第一次（且紧凑形态）出现，
  展开一次后写 localStorage 不再显示。**放在 `role="log"` 之外** ——
  塞进消息流会被读屏当成一条新消息播报。访客看到的是
  「登录之后才能回复、回应或举报」（那三件事都要登录，写成能点就是空头支票）。

验收（puppeteer，390×844 与 1440×940）：入口 28×28、`aria-expanded` 读得出、
聚焦 opacity 1、Enter 展开且焦点进操作条、Esc 收起且焦点回入口、点气泡仍能开、
桌面 0 个入口（悬停条不变）、9 档宽度横向溢出 0、控制台 0 错误、
灯箱键盘可开可关且焦点回到图片。

## 二十七、导航下那道光 / 边距 / 中栏宽度（2026-11-25 晚）

站长三条反馈：导航栏下面的光影奇怪、左右边距再小些、中间聊天框再放大些。

### 27.1 那道光是一个"假光"

页面自己铺了四团 `blur(76px)` 的 `.q-amb`，关在 `.q-chatpage__amb`
（`overflow:hidden` + 圆角 40px）里，盒子只比卡片大 12~20px。
于是光斑的可见部分**只剩卡片外沿那一圈**，顶部露出的是被裁断的硬边亮带：

- 裁切边 → 一条横线，和模糊光斑的柔和轮廓完全不搭；
- 全站还有一层 `fixed` 的 `.aurora-blob`（`-z-10`，背景装饰组件），
  两套暖光在同一片区域互相压，颜色说不清是谁的；
- 实测把 `.q-chatpage__amb` 关掉后，导航下方的像素梯度**完全连续**，没有台阶。

结论：这一层是纯负担（4 个合成层 + 4 条 26~30s 动画，只换来一条假边），
整组删掉，只留全站那层 aurora。`ChatRoom.tsx` 的 `ambience` JSX 一并移除。

### 27.2 边距与中栏：给这一页单独一套版心

1240 的版心在 1440 下给中栏只剩 548px，几乎每条消息都在折行。
`chat/index.astro` 现在给 Layout 传 `bodyClass="q-chat-wide"`，
`chat.css` 里只写一行：

```css
.q-chat-wide { --shell-max: 1600px; }
```

- 挂在 `body` 上是有原因的：Navbar 是 body 的直接子节点（fixed），
  变量挂在 `.page-shell` 里导航读不到，两者会错开一截。
- 导航 / 页脚 / 正文读的是同一对 `--shell-max` / `--shell-gutter`，
  所以三者一起变宽，横轴仍然只有一个来源。
- `:root` 上的 `--shell-max` **没动**，阅读页还是 1240（版心只允许一处）。
- `--shell-gutter` 也没动：导航胶囊靠 `-ml-4` 比正文左伸 16px，
  留白压到 1rem 以下它会顶出屏幕边缘。

实测中栏：1440 → 548 变 **748**，1280 → 593，1024（右栏收成抽屉）→ 682，1920 → 908。
12 档宽度（1920…360）横向溢出全为 0；客户端路由 `/chat/ ⇄ /about/` 来回切，
body 类与版心都跟着正确切换。

## 二十八、互联站点 / 信息栏开关 / 三栏可拖（2026-11-25 晚二）

### 28.1 左栏：这间屋子 → 互联站点

「茶室须知」那格删掉了（须知本来就在右栏「长亭的话」里，重复），


**数据不是手写名单，是按成员的 `site` 归并出来的**（`hostOf()` 去掉

### 28.2 「信息栏」为什么点了没反应

`infoOpen` 从头到尾只干一件事：给 `.q-info` 加 `is-open`，
而那个类只在 `≤1199`（右栏变抽屉）时有 `transform` 效果。
**≥1200 三栏并排时，右栏本来就在，按钮点下去什么都不动。**

现在按宽度分流（`wide` = `matchMedia('(min-width:1200px)')`）：

| 宽度 | 按钮作用 |
|---|---|
| ≥1200 | 整列收起 / 展开（`.q-bento.is-noinfo` 换成两栏模板），按下时按钮变淡 |
| <1200 | 开关右侧抽屉（原行为） |

`is-on` 只在抽屉打开时用；宽屏收起时用 `is-off`（淡），否则按钮会一直是
「按下」的粉色，看着像卡住了。`aria-expanded` + `aria-controls="q-chat-info"` 跟着走。

### 28.3 缝 14 → 8px，三栏可拖

- `gap` 从 0.875rem 收到 `--bento-gap: 0.5rem`。
- 列宽只存左右两个数（`--side-w` / `--info-w`），中栏吃掉剩下的 ——
  视口变宽时多出来的空间应该给正在读的消息流。
- 分隔条 `.q-split` 是**绝对定位**在两栏之间的缝上的 20px 透明命中区，
  视觉只有中间 3×40px 的握把（悬停 / 聚焦 / 拖动时现形）。
  缝只有 8px，纯 2px 的线根本捏不住 —— 20px 是「能不能拖」的前提。
- 拖动：指针捕获，`dx` 换算成列宽，实时夹在
  `[200,420]`（左）/ `[240,460]`（右），并保证中栏 ≥ 420。
- 双击握把复位；键盘 ←/→ 每次 16px（`Shift` 48px），`role="separator"` + `aria-valuenow`。
- 存 `localStorage: qingwu:chat-cols-v1`，进页面时恢复并**再夹一遍**

## 二十九、× 真的能收、收展有匀速动画、站点头像（2026-11-25 晚三）

站长三条：面板头上的 × 点了没反应；收起/展开要动画（匀速，收起从左边往右收，
展开从右往左）；「互联站点」那一格放站点自己的头像。

### 29.1 × 没反应，和信息栏按钮同一个病

`onClose` 只写了 `setInfoOpen(false)`，而 `infoOpen` 只驱动窄屏抽屉 ——
≥1200 三栏并排时右栏本来就在，点 × 等于没点。现在 `closeInfo()` 按宽度分流
（宽屏收整列、窄屏关抽屉），和顶栏那个按钮共用一套判断。

### 29.2 收展动画：动画的是列宽，不是 display

先把 `.q-bento.is-noinfo` 从 `display:none` 改成「第三列轨道收到 0」——
`display` 一切换就没有动画可看的。

- **方向**：右边缘不动、轨道从 312 收到 0，左边缘往右推 = 从左边收起来；
  展开反过来。`var(--dur-state)`（340ms）+ `linear`（匀速），不是缓入缓出。
- **内容不许重排**：动画期间把 `.q-info > *` 的 `min-width` 钉在全宽
  （`calc(var(--info-w) - 2px)`）。不钉的话每收一帧文字就重折一次行，
  看着像被攥扁，而不是被右墙擦掉。
- **边框**：0 宽时 1px 边框还会画出来，所以 `visibility: hidden` 用
  `transition-delay: var(--dur-state)` 延到动画结束；展开时基态没有延时，立刻可见。
- **过渡只在按钮触发时开**：`.is-anim` 类由 JS 加、360ms 后摘（时长比 `--dur-state` 多 20ms 余量）。
  常开的话，拖分隔条和改窗口大小都会被这 300ms 拖住（整栏像在糖浆里）。
- **无障碍**：收起后那一列 DOM 还在，必须 `inert` + `aria-hidden`，
  否则 Tab 会跳进看不见的面板里。

### 29.3 缝隙从 grid-gap 改成 margin（为了 0 宽轨道）

`gap` 对「0 宽度的轨道」也会供货：第三列收到 0 之后，右边还留着一条 8px 空档，
中栏右缘就比版心短一截；而 gap 没法只对某一条缝生效。

所以改成：`column-gap: 0`，轨道写成 `calc(var(--side-w) + var(--bento-gap))`，
缝由 `.q-side { margin-right }` / `.q-info { margin-left }` 供货。

两者是一组，改一个不改另一个就会在底部多出一段空白。

### 38.2 已读：加对勾、加「谁读的」

后端 `poll` 的 `reads` 原来只有 `{id, n}`（COUNT）。现在多一个 `names`：

- 用 `chat_reads.last_read_id >= 我最新那条 id` 反推谁读到了（同一条口径）；
- 一次查询同时给出人数和名字，`LIMIT 200`（这间屋子真到几百人，回执也没意义了）；
- 名字取前 5 个，只用于悬停提示。

前端：`✓✓ 已读 1`。对勾不是装饰 —— 扫一眼就看到，比「已读」两个字快；
`title` 是「test 已读」，多人时「A、B 等 3 人 已读」。

**只挂在「我最新那条」上**这一点没变：每条都算的话一屏十几条自己的消息要十几次查询，
而实际对话里也只有最后一句的「已读」有意义（WhatsApp 同样的取舍）。

### 38.3 正在输入：头像 + 会动的点 + 4 秒粘滞

- **头像**：名字前面叠一到两枚小头像（从在线名单按名字取），名字可能是「茶客#7」，
  头像一眼认得。
- **三个点真的在动**：原来那三个点是静态的，看着像三个删除线。
  新增 `@keyframes q-typing-dot`（1.1s，三个点各延迟 0.18s）。
  ⚠️ 按站内纪律同时挂进 `motion.css`：`.qhidden` 里 `animation-play-state: paused`、
  `prefers-reduced-motion` 里 `animation: none`（停下来就是三个静止的圆，文字本身已说明状态）。
- **4 秒粘滞**：后端窗口 6 秒、两次 poll 之间 2.5 秒，边缘时机容易抖成「闪一下又没了」。
  前端按名字记最后一次被报到的时刻，多留 4 秒 —— 只比 poll 间隔长一点。

### 38.4 验收

双会话实测（清吾 / test）：「test 正在输入」带头像、3 个点都在动画；
`已读 1` 带对勾、`title="test 已读"`；对比度 229 节点 0 失败、命中区 0 个 <24、
三档宽度 0 溢出、控制台 0 错误。
