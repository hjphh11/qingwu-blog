# 审核清单 · 聊天室

> ✅ **2026-11-27 核对：内容与现状一致，未改动**（只补了这行核对标记）。

> 本文是 `docs/方案-聊天室.md` §5 的展开。
> 站长定的口径：**发送时先过本地清单，清单没命中就直接放行，之后再做异步 AI 后审。**
> 本文把「清单」写成可执行的样子，并说明它和 AI 后审怎么衔接、怎么观测。

---

## 一、先说清楚清单不该做什么

评论区的审核是「每条都交给模型判」，因为留言是异步阅读的，慢一点没关系。

聊天不一样，有两个硬约束：

1. **不能加延迟。** 本地清单必须全部是常数时间判断（正则、字符串比较、计数），一条消息的判定成本要 <1ms。任何需要「理解」的判断都不许进清单。
2. **不能靠关键词一刀切。** 中文里关键词误伤率高得离谱：
   - 「色情」会出现在「我在做内容审核，色情图片怎么识别」里
   - 「赌博」会出现在「这游戏机制像赌博」里
   - 「毛」在某些语境是骂人，在另一些语境是姓氏

   所以：**单词命中不等于违规**。清单只处理两类东西 —— 几何特征（长度、链接数、重复度、频率）和组合特征（黑话 + 联系方式同现）。

> 一句话原则：**清单负责挡「不需要理解就能判」的，AI 负责判「需要理解才能判」的。**

## 二、四种处置动作

不是「拦 / 不拦」二选一。中间那档才是关键：

| 动作 | 行为 | 用在什么情况 |
|---|---|---|
| `block` | **不落库**，回 `200 {ok:false, silent:true}`，前端在输入框附近显示一行中性说明 | 几何特征已经确定的垃圾（纯链接刷屏、重复刷屏、频率熔断） |
| `hold` | 落库 `status='pending'`，**只有发送者自己看得见**，不进 poll 广播 | 疑似有风险但可能误伤（联系方式、新账号首条） |
| `flag` | 正常落库 `visible`，但进 AI 队列并**提高优先级** | 轻度可疑（外链、轻度脏话、引流词） |
| `pass` | 正常落库 `visible`，进 AI 队列普通优先级 | 绝大多数正常消息 |

`hold` 这个设计值得多说一句：它解决的是「拦错了怎么办」。直接拒绝会把人赶走（尤其新来的，第一句话就被挡，再也不会来第二次）；`hold` 让他自己看得见、正常显示在界面里，别人看不见，AI 判完一般是几秒内出结果——**绝大部分 hold 会在一两秒内转成 visible 并广播出去**，本人几乎无感。真正被判违规的才永久停在 pending。

## 三、清单正文

### L0 · 硬拦（`block`）

全部是几何特征，不涉及语义。

| # | 规则 | 判据 | 为什么不需要理解语义 |
|---|---|---|---|
| 0-1 | 超长 | 正文长度 > 500 字 | 纯计数。聊天不是发文的地方 |
| 0-2 | 纯链接 | 去掉所有 URL 后可见字符 < 4，且 URL 数 = 1 | 聊天室里发一条只有链接的消息，没有正常用途 |
| 0-3 | 链接堆叠 | 单条 URL 数 ≥ 3 | 同上，且是典型 SEO 灌水形态 |
| 0-4 | 重复刷屏 | 与该账号最近 5 条历史**完全相同** | 字符串相等比较 |
| 0-5 | 连发间隔 | 距上一条 < 1.2 秒，且已连续 5 次 | 计数。正常人打字不会这么准 |
| 0-6 | 频率熔断 | 60 秒内 > 15 条 | 计数。超了就禁言 5 分钟（不是永久） |
| 0-7 | 黑域名 | URL 主机名命中黑名单 | 精确匹配。名单人工维护，见 §4.3 |
| 0-8 | 高危组合 | 黑产话术词 **且** 同一句里有联系方式形态 | **组合**才拦。单出现「刷单」不拦（可能在讨论反诈），配着手机号/微信号一起才拦 |

> 0-5 和 0-6 为什么要分开：0-5 抓的是「脚本连发」（节奏太整齐），0-6 抓的是「人肉刷屏」（节奏正常但量太大）。处置也不同：0-5 直接 block 这条；0-6 触发 `chat_bans` 写一条 5 分钟临时禁言。

### L1 · 可疑（`hold` 或 `flag`）

需要一点判断，但规则能给出可靠信号。

| # | 规则 | 判据 | 动作 | 理由 |
|---|---|---|---|---|
| 1-1 | 手机号 | `(?:\+?86)?1[3-9]\d{9}` 且前后不是数字 | `hold` | 聊天室里贴手机号，正常场景极少 |
| 1-2 | 邮箱 | 常见邮箱正则 | `flag` | 比手机号常见（有人会留联系方式交流），放宽一档 |
| 1-3 | 微信号 | `(微信|vx|V信|威信)\s*[:：]?\s*[a-zA-Z0-9_-]{4,}` | `hold` | 「加微信」就是引流的标准句式 |
| 1-4 | 引流词 | 加微 / 私聊 / 扫码 / 点击领取 / 优惠券群 / 代运营 / 接单 / 接推广 | `flag` | 单词命中只 flag，不 hold——「私聊」也可能是在说「这事私聊说」 |
| 1-5 | 外链 | URL 主机不在白名单 | `flag` | 白名单 = 友链域名 + github/gitee/mdn/stackoverflow/bilibili 等常见站 |
| 1-6 | 轻度脏话 | 脏话词表（见 §4.2） | `flag` | **不 hold**。聊天里骂一句不新鲜，藏起来反而显得诡异；让 AI 判语境 |
| 1-7 | 新账号 | 注册 < 24 小时 **或** 累计发言 < 5 条 | `flag` + 队首 | 新人不是嫌疑人，但值得先看一眼。老熟人不受影响 |

### L2 · 免检（直接 `pass`，但仍进 AI 队列）

| # | 规则 | 判据 |
|---|---|---|
| 2-1 | 站长 | `accounts.role = 'admin'` → **完全跳过 AI**（自己人不需要审自己） |
| 2-2 | 纯表情 | 只有 `:[key]` token 且数量 ≤ 6 |
| 2-3 | 极短 | ≤ 4 字，且不含链接、不含联系方式形态 |

> 2-1 是唯一「连 AI 都跳过」的分支。其余免检只是跳过清单，AI 照判 —— 因为清单本来就不判语义。

## 四、词表怎么组织

### 4.1 结构

词表不能写成一个大数组。每条规则要能被单独观测、单独关掉、单独统计命中数：

```ts
type Level = 'L0' | 'L1' | 'L2';
type Action = 'block' | 'hold' | 'flag' | 'pass';

interface ScreenRule {
  id: string;          // 'L0-4'，后台按它统计
  level: Level;
  action: Action;
  /** 纯函数，常数时间，不许 async、不许查库 */
  test: (text: string, ctx: ScreenCtx) => boolean;
  /** 一句话说清为什么有这条 —— 半年后靠它判断能不能删 */
  why: string;
  /** 站点设置里能不能关（几何类规则不可关，语义类可关） */
  togglable: boolean;
}

interface ScreenCtx {
  accountId: number;
  role: string;
  recentBodies: string[];   // 该账号最近 5 条（查库，调用方给）
  lastTs: number;
  minuteCount: number;
  accountAgeHours: number;
  totalMessages: number;
}
```

`recentBodies / minuteCount / accountAgeHours` 需要查库，但**只查一次**（send 入口一次查出，喂给所有规则）。规则本身保持纯函数，这样能单测。

### 4.2 词表（起点，不是终点）

分四组，注意**组的作用域不同**：

```
高位（进 0-8 高危组合才生效，单独出现不拦）：
  刷单 / 代开发票 / 博彩 / 私彩 / 棋牌室 / 包赢 / 稳赚 / 日赚 / 躺赚
  约炮 / 裸聊 / 一夜情 / 福利视频 / 资源站
  代运营 / 站群 / 外链出售 / 权重 / 排名优化

引流（1-4，单词命中 flag）：
  加微信 / 加vx / 私聊 / 扫码 / 二维码 / 点击领取 / 优惠券 / 群号
  接单 / 接推广 / 合作推广 / 引流

脏话（1-6，单词命中 flag，永不 block）：
  ※ 这里刻意不展开完整词库，两个原因：
    ① 写在文档里等于给出规避清单；
    ② 真词库会持续变，应该在 worker/src/chat/words.ts 里维护，跟着代码走。
  做法：以「常见侮辱性词汇 + 地域歧视 + 性别歧视」三类各取 20~30 条起步，
        运行后看 /admin/chat 的命中统计再补。

黑域名（0-7，精确匹配主机名）：
  初期留空。出现第一条再手工加，不预先堆一份从网上抄的名单
  —— 那种名单半年就全过期，还会误伤被挂马的正经站。
```

**「高位词单独出现不拦」这条必须坚持。** 举个实例：有人在聊天里问「这游戏是不是赌博机制」，命中「赌博」，但语境完全正常。如果单词就拦，这类正常对话全被吃掉，聊天室就死了一半。

### 4.3 白名单（1-5 用）

```
友链域名（从 src/data/links.json 自动生成，不手抄）
+ 通用技术站：github.com gitee.com developer.mozilla.org stackoverflow.com
              bilibili.com zhihu.com juejin.cn
+ 本站：qingwu.ink www.qingwu.ink
```
从 `links.json` 自动生成是关键——友链加了新人，白名单跟着变，不用手工同步两处。

## 五、和异步 AI 后审怎么衔接

```
POST /chat/send
  │
  ├─ ① 一次查库：取账号资料 + 最近 5 条 + 1 分钟内条数
  │
  ├─ ② screen() 纯函数过一遍清单  →  { action, hits: ['L0-3','L1-5'] }
  │
  ├─ ③ 按 action 落库
  │     block → 不落库，直接 200 返回
  │     hold  → status='pending'
  │     flag  → status='visible'，同时写 moderation 队列（priority=high）
  │     pass  → status='visible'，写队列（priority=normal）
  │
  ├─ ④ 立刻返回（前端 100ms 内看到自己的话）
  │
  └─ ⑤ waitUntil(judgeAll)
        ├─ hold 的优先判（有人在等）
        ├─ pass 的按正常顺序
        ├─ 判定结果：
        │    ok      → status='visible'（hold 的在这里被放出来并广播）
        │    命中    → status='spam'
        │              → poll 的 recalled 里带上 id，别人界面上消失
        │              → 发送者看到一行灰字「这条被拦下了」
        └─ judge 挂了 → hold 转 visible 放行，flag/pass 不动
```

三个细节：

**① hold 的消息不进 poll 广播。** 否则「只有自己可见」就成了空话。poll 里对 `status='pending'` 的消息加 `account_id = 自己` 的过滤条件。

**② hold 转 visible 时要能被别人拉到。** poll 是 `WHERE id > ?`，一条 `id=100` 的 pending 消息在 `id` 涨到 200 之后才转 visible，别人永远拉不到了。所以需要一个 `released` 字段（或复用 `ts` 更新），poll 额外查「最近 60 秒内从 pending 转 visible 的消息」。**这个坑不写清楚，实现时必踩。**

**③ AI 调用量要单独算。** 现有 `AI_DAILY_LIMIT=300` 是给评论的。聊天一天两三百条就会撞额度。三条路：
- 给聊天单独一个额度（推荐）
- `pass` 的消息按 50% 采样审核（成本减半，漏判概率上升）
- 只审 `flag` 和 `hold`，`pass` 完全不审

我倾向第一条 + 保留全量审核。理由是 Jev 输出不计费，200~350ms 一次，成本主要是调用次数而不是钱。真要省，先看 `/admin/chat` 的统计数据再决定，别提前优化。

## 六、清单本身要被观测

这是最容易被跳过、但半年后最要命的一环。

每条规则都要记两个数：**命中次数** 和 **误伤次数**（站长在后台点「这条没问题」的次数）。

- 某条规则命中 500 次、误伤 0 次 → 说明有用，可以升档（flag → hold）
- 某条规则命中 3 次、误伤 3 次 → 说明是噪音，删掉
- 某条规则命中 200 次、误伤 80 次 → 判据太宽，回去改正则

没有这个数，清单就只是一份「当初觉得有道理」的静态文件，半年后没人敢动。

后台 `/admin/chat` 需要一个「规则」tab：每条规则一行，展示 `id / why / 命中 / 误伤 / 开关`。

## 七、边界

| 不做 | 理由 |
|---|---|
| 前置验证码（Turnstile） | 聊天每句话都验一次，人会被烦走。只在注册/登录那一步有就够 |
| 自动封号 | 命中就封是灾难。`block`/`hold` 只作用于当前这条，封禁必须人工 |
| 敏感词全文库 | 中文没有可用的公开词库，抄来的要么过窄要么误伤一片 |
| 对发送者解释「你违反了第 X 条」 | 等于给出绕过说明书。只说「这条没发出去，换个说法试试」 |
| 图片消息审核（v1） | v1 不发图，评论里的图片走外链。等 v2 上图片时再单独设计（那是另一个量级的事） |

## 八、和现有系统的关系

| 现有 | 关系 |
|---|---|
| `admin/ai.ts` 的 `moderateComment` | **直接复用**，不新写一套。只是调用时机从「同步」改成「异步」，并把五类口径原样带过去 |
| `VERDICT_DESC`（五类口径） | **不改**。清单里「高位词」那些其实就是五类的粗筛，语义判断仍归 AI |
| `moderation_log` 表 | 复用，加一列 `source='chat'` + 一列 `hits`（JSON，记是哪些规则命中的） |
| `/admin/review` | 不动。聊天室的审核记录单独在 `/admin/chat` 看，因为场景不同（一个是楼，一个是流） |
| `chat_bans` | 新建。0-6 频率熔断写临时禁言，人工封禁也写这张表 |
