> 目标：在 `www.qingwu.ink/admin` 直接访问的后台，做成「朝朝听雨的小爱后台」那样的形态，
> 视觉换成本站的爱弥斯暖色系。登录走**账号密码 → 邮箱验证码**两级。
>

## 二、从他 18 张截图反推的信息架构

后台是**单页 + 顶部 tab**，不是独立 URL 的多页。六个主模块：

| 模块 | 对应截图 | 核心内容 |
|---|---|---|
| 登录 | `login` `login-verification` | 左栏品牌 + 三步说明，右栏账号/密码/验证码 |
| 评论收件箱 | `comment-inbox` `comment-ai-reply` | 表格（访客/内容/情绪/意图/审核/回复状态），行内展开回复区 |
| 运行与设置 | `moderation-settings`（动图，未取到） | 模型参数、回复范围、路径黑白名单、关键词、安静时段、每日上限、运行日志 |
| 评论审核 | `moderation-rules` `moderation-test` | 规则权重与阈值、测试页（显示判定 + 各项概率 + 访客看到的提示） |
| 友链审核 | `friend-application-actions` `friend-review-detail` `friend-comment-review` `friend-management` `friend-drag-sort` `friend-status-menu` `friend-unavailable` `friend-violation` | 三个子页：待处理申请 / 已收录 / 仓库设置 |
| 回链检查 | `backlink-checks` | 三列卡片，每站一个「重新检查 / 指定检查页 / 管理状态」 |

**几个值得抄的交互**（截图里能看出来的）：

1. **行内展开**而不是跳详情页 —— 评论点「回复」直接在当前行下面铺开编辑区，上下文不丢。
2. **暂存 + 批量提交** —— 顶部常驻「待提交改动 N」，弹窗逐条列出「字段：旧 → 新」并可单条撤销，最后合成一次提交。
3. **拖拽排序** —— 卡片右上角点阵把手，按住后整张卡跟随、虚线框表示落位，键盘也能操作（空格抓取 / 方向键 / 空格放下 / Esc 取消）；提示条写明「排序未暂存，和其他改动一起提交」。
4. **状态带倒计时** —— 短暂失联 30 天、违规整改 7 天，到期文案变「将于 3 日内清除」。
5. **草稿不丢** —— 回复草稿存浏览器本地，发送成功才清；AI 返回时保留用户期间手打的内容。

## 四、落地形态（关键：零 nginx 改动）

现在这套是「Astro 静态 + 本地 workerd」：

```
浏览器 → nginx → /              → dist/client（静态）
               → /api/*         → 127.0.0.1:8787（workerd）→ 本地 SQLite
```

`try_files $uri $uri/index.html $uri/ =404` 已经能把 `/admin` 解析到 `/admin/index.html`，
`/api/` 也已经整体反代到 Worker。所以：

- **前端**：`src/pages/admin/index.astro`（登录页）+ `src/pages/admin/console.astro`（控制台）。
  **保持静态预渲染，不引 SSR** —— 香港机跑的是 workerd，一旦用了 `prerender=false`
  就会和 Vercel adapter 绑死，搬不过去。数据全靠客户端 fetch。
- **后端**：Worker 新增 `/admin/*` 路由，实际 URL 是 `/api/admin/*`，**nginx 一行不动**。
- **组件**：Astro 壳（管布局、字体、无闪白）+ React 岛（管表格/弹窗/拖拽）。项目已有 React 19。
- **SEO**：`/admin` 加 `<meta name="robots" content="noindex,nofollow">`，`robots.txt` 加 `Disallow: /admin`。

## 五、认证：两级 + 会话

```
① 账号 + 密码  →  ② 6 位邮箱验证码  →  ③ HttpOnly cookie 会话（30 天）
```

**为什么要两级**：站点公网可访问、`/admin` 也不藏。单密码被撞就全丢了；
二级验证码等于给后台加一个"必须拿到邮箱"的门槛，且天然带限流。

- 密码：PBKDF2-SHA256 / 150k 迭代 / 随机盐（Web Crypto，workerd 原生支持）。
- 验证码：6 位数字，5 分钟有效，**60 秒发送冷却**，最多试 5 次；
  存 `code_hash` 不存明文。发信走现成的 `qingwu-mail` 中继（QQ SMTP，500 封/天）。
- 会话：32 字节随机 → SHA-256 存库；cookie `HttpOnly; Secure; SameSite=Lax; Max-Age=30d`。
  **只在服务端校验**，前端拿不到 token 原文。
- 限流：同一 IP 15 分钟内失败 15 次 → 锁 15 分钟；每次登录尝试都记 `ip_hash`（复用 `HIT_IP_SALT`）。
- 首次初始化：不给页面注册入口。用一条 CLI/SQL 插入管理员（`scripts/create-admin.mjs`），
  密码本地哈希后写入，避免任何"初始化页面"变成后门。

**新增表**（迁移 `worker/migrations/0013_admin.sql`）：

| 表 | 字段要点 |
|---|---|
| `admin_users` | `id` / `username` (UNIQUE) / `pass_hash` / `salt` / `email` / `created_at` / `last_login_at` |
| `admin_sessions` | `token_hash` (PK) / `user_id` / `created_at` / `expires_at` / `ip_hash` / `ua` |
| `admin_codes` | `id` / `user_id` / `code_hash` / `sent_at` / `expires_at` / `tries` |
| `admin_attempts` | `ip_hash` / `ts` / `ok`（算限流用） |

## 六、数据：哪些直接读本地库，哪些要动仓库

这是整套里唯一有"架构重量"的地方，必须先讲清：

| 功能 | 数据来源 | 写入方式 |
|---|---|---|
| 评论列表 / 审核 / 回复 | D1 `comments` | 直接 UPDATE/INSERT（**已在主库**） |
| 友链申请 | D1 `applications` | 直接 UPDATE（主通道是评论区留言，见 README-hk） |
| 友链资料（名称/头像/描述/排序/推荐） | **`src/data/links.json`（仓库）** | 只能改仓库 → push → 服务器 `git pull` + build |
| 友链展示状态（失联/违规倒计时） | 建议新表 `friend_status` | 直接写 D1，前台读接口 |
| 回链检查结果 | 新表 `backlink_checks` | cron 每日写 |
| 访问统计 | D1 `hits` / `daily_stats` | 只读 |

**友链资料那条是硬骨头**：`links.json` 在 Git 里，后台要改就得走 GitHub Contents API
（拿文件 SHA 做乐观锁 → PUT → Actions/服务器拉取构建）。朝朝听雨折腾最久的就是这块。

我们有两阶段性做法：

- **P2 先做「半自动」**：后台只管审批和状态，通过后**生成一段可直接粘贴的 JSON 片段**
  并给出 `git` 命令 —— 人确认后执行。零风险，先跑起来。
- **P3 再做「全自动」**：接 GitHub PAT（细粒度，只授权该仓库 contents:write），
  实现 SHA 乐观锁 + 提交 + 触发构建。**这一步要单独评估**，因为它让后台获得了改仓库的能力。

## 八、要先定的三件事

1. **AI 要不要**：他背后接的是 Jev 模型。我们没有模型通道，要做得先定用哪家、
   key 放哪（Worker secret）。建议 P0~P3 都不依赖 AI，先跑通人工流程。
2. **友链是否允许后台直接改仓库**：决定 P2 走「半自动出片段」还是直接上 P3「全自动提交」。
3. **管理员用什么邮箱收码**：中继是 QQ SMTP，收件人可以是任意邮箱（发件人才受限）。

### 实际做出来的和这份方案的三处偏差

1. **「半自动 → 全自动」没有分两期，代码里两条路并存。**
   有 `GITHUB_TOKEN` 就直写仓库；没有就降级返回成品 JSON 让管理员粘贴。
   **目前 PAT 还没配，所以线上跑的是半自动那条。**
   这比原计划好：不用等 PAT 到位才能用，配了自动切换。

2. **「暂存批量提交」按原样做了，但只覆盖 links.json 那部分。**
   申请审批仍是即时的（写 D1 立刻生效）。两者在界面上刻意分开：
   申请卡的按钮是实心 primary，已收录的行内按钮全是 ghost，
   只有顶部 savebar 的「提交到仓库」是实心。
   —— 混用实心按钮会让站长以为自己已经改完了。

3. **多做了「自动部署」，方案里没写。**
   不做的话 P2 的验收标准「前台立刻可见」根本达不到 ——
   后台提交完还得人工登服务器 pull + build。
   `scripts/auto-deploy.sh` + `qingwu-deploy.timer`（2 分钟一轮，flock 防并发）。

### 回链检查的实测口径（下次别重新发明）

- 规则极宽：页面里出现 `qingwu.ink` 就算，不带协议头也算。
- 首页没命中就看候选页：先取首页 href 里的友链链接，再补
  `/links/ /friends/ /link/` 三个常见路径，最多 3 页。https 失败回落 http。
- **必须流式读**：rainzt.cn 首页 983KB，先截断到 400KB 再搜索必然漏判。
- 已知局限：SPA 站点的回链在前端渲染后才出现，raw HTML 抓不到 ——
  这类站点会被判成「无回链」，需要人工看一眼。
- 2026-11-10 全量跑 14 个友链：**7 有 / 7 无**，无的逐个核过，是真没给。

### 还没做的

- **P4 AI 辅助**：需要选模型、定 key 放哪（Worker secret）。
  按方案第八节的原则，前三个阶段都不依赖 AI，现在就处在「全人工也跑得通」的状态。
- **friend_status 前台接入**：表建好了、后台能改，但前台还没读
  `/link-status` 接口 —— 也就是说「失联 30 天倒计时」目前只在后台可见。
- **Vercel 项目的 git 自动部署还没断**（需在 Vercel 后台操作）。

## 十一、第三轮：站长砍掉的三样东西（2026-11-10 晚）

### 1. 试判面板删了

第一轮做的「贴一段文字试试会不会被拦」，站长看过说没用。判断是对的：
他真正要的是「每条留言都判」，不是「拿样例调参数」。阈值和类别的正确性
不该靠人肉试出来，而该靠真实的误判反馈 —— 收件箱「垃圾」里能放行，就是反馈通道。
接口 `POST /admin/review/test` 一并删掉，它是全后台唯一收裸文本的端点，留着也是个洞。

### 2. 审核不再有总开关，类别改成法律口径

原话：「评论规则是用户发的消息都要判断，规则要符合法律。」

- **`judge.on` 删了**。开关一关就等于「留言随便发」，那不叫配置，叫漏。
  现在只有「有 key 就判、没 key 判不了」两种状态，没 key 时页面上直接警告。
- **类别从 3 类扩成 5 类**，键名也换了：`illegal` 违法违规 / `porn` 色情低俗 /
  `abuse` 侮辱攻击 / `privacy` 隐私侵权 / `spam` 垃圾广告。
  违法信息与不良信息的划分参照《网络信息内容生态治理规定》；
  垃圾广告不算违法内容，单独一类 —— 它最常见，混在违法里判会拉偏阈值。
- **`judge.action`（hold / reject）删了**，固定落 `spam`。给两个选项只会让人以为
  「压到待审」和「标垃圾」差很多，其实访客那边一样：都不显示。
- **`judge.notice`（命中时给访客看的话）删了**。既然垃圾直接不展示，
  就没有「压下来了，等我手动放出来」这回事；何况告诉对方「你被拦了」
  只会方便他改一版再来。
- 口径文案收在 `settings.ts` 的 `VERDICT_DESC`，**提示词 / Jev 的 criteria /
  后台页面说明三处共用**。改规则只改那一处。

旧库里的四个键由 `0019_admin_review_cleanup.sql` 清掉。
`judge.categories` 也一起清 —— 旧值 `spam,abuse,privacy` 在新的五类里凑不出一组有意义的组合，
留着就是「看起来生效、其实漏判」。

### 3. 收件箱里的「待审核」是伪概念

原话：「评论由 AI 回复，应该没什么待审核的吧，待审核应该是[友链审核]那里审核。」

对。留言在提交那一刻就判完并生效了，不存在「堆在后台等人点通过」。
收件箱的 tab 改成 **全部 / 已通过 / 垃圾**，人工审核只留在友链申请那边。

顺带修掉一个真 bug：`status` 字段被当成两个意思用 —— 既是「上墙了没有」，
又被当成「审核过没有」。`pending` 在后台叫「待审核」、在前台叫「等我看看」，
同一个值两种解读。现在明确：**`pending` = 还没收录进友链墙**，与内容审核无关。

`GET /friends-board` 也补了 `status IN ('visible','pending')`。
之前 `status != 'deleted'` 把 `spam` 也返给前台 —— 拦了等于没拦，
这是审核功能上线后最不该留的一个口子。

### 4. 友链「推荐」撤了

比全都没有更糟。以后要做，从这笔 commit 里捞。

## 十二、第四轮：拦住之后要能复盘 + 拆页 + 统计（2026-11-10 晚）

站长三句话，对应三件事：

### 1. 「在这下面添加一个拦截记录」→ `0020_moderation_log.sql`

在这之前，审核拦下一条留言只会把 `comments.status` 改成 `spam` ——
**为什么拦、多少分、阈值多少、模型给了什么理由，全在日志里滚掉了**。
收件箱只告诉站长「这条是垃圾」，恰恰说不出他最想知道的那句「凭什么」。

于是加一张 `moderation_log`：

| 列 | 为什么单独存 |
|---|---|
| `comment_id` **唯一** | 审核只在提交那一刻发生一次；重复写没有意义 |
| `verdict / score / threshold` | 阈值会变，**记录必须留当时的原值**，否则事后看会得出错误结论 |
| `reasons`（JSON，最多 3 条） | 列表里直接列出来，不用再点开 |
| `day` | 统计要按天出柱状图；用 ts 现算时区迟早错一次 |

三条纪律：
- **记录失败绝不影响主流程**（`recordModeration` 全 try/catch）。记不下日志是「少一条证据」，不是「这次提交失败」。
- **一条留言一行，放行不删行**。「当时判成垃圾、后来人工放行」本身就是有用的事实；当前是否还拦着看 `comments.status`，一张表只回答一个问题。
- **历史数据要补齐显示**：功能上线前落的 `spam` 没有日志行，列表用第二段查询从 `comments` 现补（`detailed=false`，显示「历史记录，无判定详情」），否则站长会以为一条都没拦过。

### 2. 「把运行与设置分开页面」→ `/admin/status` + `/admin/settings`

一页里既有只读数字又有可改表单，看的时候想改要滚很久，改的时候又怕碰错旁边的东西。
拆开之后职责单一：**运行状态只看，设置只改**。顶栏从四项变六项（另加「统计」）。
窄屏不再靠横滑 —— ≤860 隐藏图标、padding 收到 6px，390 宽刚好放下六项。

顺带修了两处语义残留：`pending` 在运行状态页还叫「待审核」（应是「未收录」），
自动回复那段还写着「四道闸」（实际已是六道）。

### 3. 「统计数据单独一个页面，要图表，有加载动画」→ `/admin/stats`

`GET /admin/stats?days=7|14|30`。访问部分**直接复用对外 `/stats` 的 `buildStats()`** ——
同一个站点不该有两个 PV 数。它没有的那几路（评论、拦截、AI 用量、自动回复）自己查，
一律在 JS 里按 `dayKey` 分桶并**补空天**：图表按下标画，缺一天后面所有柱子会左移一格。

图表**全部手写**，一个库都没引：

| 形状 | 实现 | 为什么 |
|---|---|---|
| 折线 + 面积 | SVG，viewBox 720×200 + `preserveAspectRatio="none"` + `vector-effect: non-scaling-stroke` | 桌面和 390 共用一套坐标，不用 ResizeObserver 重算；线宽不被拉伸 |
| 并排柱 | DOM（flex + height %） | 一次 CSS transition 的事；SVG 里要 `scaleY` + `transform-box`，多一层不可靠的东西 |
| 横条榜 | DOM | 同上 |

为四张图引 ECharts（≈300KB）/ recharts（≈90KB + d3）不划算，何况它们默认配色和圆角
跟这套黑白点阵完全不是一回事，改样式比画还费时间。

**加载动画分两层**：
1. 数据没到 → 骨架屏（`.q-skel` 的 shimmer）。接口本机 20ms 就回来，骨架常常只闪一帧 —— 这是对的，不要为了「看得见」加人为延迟。
2. 数据到了 → 图自己长出来：柱子从 0 长高、折线用 `pathLength=1` + `dashoffset` 描出来、KPI 数字 rAF 数上去。**这一层每次加载都会播**，是真正看得见的那个动画。

两层都走 `prefers-reduced-motion`：关掉之后直接给终值，不做位移。

### 4. 踩到的两个坑

- **`SELECT ... AS to` 在 SQLite 上是语法错误**（`TO` 是它的关键字）。整条 AI 用量查询失败，
  而 `rows()` 当时把异常吞了 → 接口返回 200、那张图全 0，看起来像「这几天没用 AI」。
  修法：别名改成 `tkout`；同时给 `rows()` 加 `warnings` 收集，页面上把「哪一块没读出来」
  明写在警告框里 —— **静默的 0 比报错更难查**。
- `astro check` 会对 `worker/**` 报一堆隐式 any / `ExecutionContext` 找不到，是已知的
  （worker 有独立 tsconfig）。看错误只数 `^src/` 开头的行，worker 用 `cd worker && npx tsc --noEmit`。

## 十三、第五轮：去掉两个限额、补模型设置、统计照别人家的信息架构（2026-11-10 深夜）

### 2. 「模型设置呢」→ 设置页第二块重做成两条通道

以前只有一格「模型」输入，藏在「生成参数」里，页面上根本看不出这台站用什么模型。
现在按通道摊开：`writer`（起草）与 `judge`（判定）各一张卡，写清楚

- 当前生效的模型名 + 它是「本页指定」还是「跟随环境变量」
- 今日用量 / 配额（进度条，≥80% 转黄、满转红）
- 协议（judge 会标「决策协议」还是「OpenAI 兼容」）
- 「测一下」按钮直接打 `POST /admin/status/ping`，两条通道各自出结果

可改的仍然只有 `writer.model` / `temperature` / `maxTokens`。
**judge 的模型与地址故意只读**：换判定模型必须重新调提示词，随手在网页上改会让判定
静默失败（fail-open 之后就是「全都不拦」）。同理 key 也不上网页 —— 它还在 `.dev.vars`。

通道快照走单独的 `GET /admin/status`，不塞进 `/settings`：judge 的协议判定在 `ai.ts`

### 3. 统计页照参照站重排（学信息架构，不学皮肤）

看了 `rainzt.cn/analytics/` 的模块清单，值得抄的是**顺序与维度**：

| 他家 | 我们 | 说明 |
|---|---|---|
| 四张摘要卡（累计访客/浏览、今日访客/浏览） | `SummaryStrip` | 与区间无关，标清楚「开站以来」 |
| 访问脉冲（7/30/90 天 + 环比 + 活跃天数 + 单日峰值） | 访问脉冲面板 | 区间 7/14/30；四个数挪到图下面 |
| 大家在看什么（带 01/02 序号） | 页面榜加 `.q-rank__i` | 序号比纯横条更容易念「第一名是谁」 |
| 流量来源（直接/搜索/外部 + 明细） | `SourceSplit` + 主机榜 | 以前把 direct 过滤掉了，占比分母却是总 PV |
| 访客活跃时间（7×24 热力 + 最活跃时段/星期/夜间占比） | `HeatMap` | **替掉了原来「一天 24 根柱子」**，周中与周末的作息本来就不同 |
| 设备与浏览器 | 只有设备 | `hits` 没有 browser 列，加字段也补不回历史 |
| 访客地域 TOP5 | 地区榜 | 已有 |
| 推送节奏（GitHub commit 热力） | 不做 | 我们没有可公开的推送源，更新日志在 `/changelog` |
| 最近评论 | 不做 | 收件箱里就是 |

后端 `GET /admin/stats` 因此多了三样：`summary`（allTime / today / activeDays / peak）、
`heat`（扁平 168 项，索引 `w * 24 + h`，`w` 已从 `%w` 的 0=周日 挪成 0=周一）、
`sources`（direct / search / external）。

**UV 有两个口径，页面上必须说明**：顶部「累计访客」是 `COUNT(DISTINCT visitor)` 全站去重；
「本周期访客」是每天 UV 相加，同一人跨天会重复计。所以后者比前者大是正常的 ——
不写这句，下次一定有人来问「为什么 14 天访客比累计还多」。

### 4. 这一轮的三个小坑

- **flex 子项默认 `min-width: auto`**：热力图是 24 列 grid 装在 flex 列里，390 宽时
  它按内容宽度撑开、被面板圆角裁掉右边两列。加 `.q-heat > * { min-width: 0 }` 才对。
  同类问题柱状图也有 —— 那里的成因是首末标签 `left: 50%` 居中后各有一半落在盒子外。
- **`referrer` 里空串、NULL、`(direct)` 是三种写法**，`GROUP BY` 出来会是多行同义的
  「直接访问」，而 `sources` 又把它们加在一起，两处数字对不上。查询里统一成
  `COALESCE(NULLIF(referrer, ''), '(direct)') AS k`。
- **`hits` 里没有浏览器列**，所以「设备与浏览器」只做了前半。要补就得动 `0001` 之后的
  schema 与 `/hit` 写入，而且历史数据仍然是空的 —— 这一轮不值得。
