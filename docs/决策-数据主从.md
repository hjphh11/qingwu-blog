# 决策：数据主库定为香港服务器本地 SQLite（2026-11-10）

> 状态：**已定**。
> 主库 = `103.79.185.65` 上的 `/data/qingwu/worker/.wrangler/state/v3/d1/**/*.sqlite`。
> CF D1（`qingwu`，`b4bba833-…`）降级为**只读归档**，不再接受写入。

## 为什么现在要定这件事

2026-11-10 01:40 域名 A 记录切到香港机后，实际上同时存在两个「线上」：

| 入口 | 背后 | 状态 |
|---|---|---|
| `https://www.qingwu.ink` | 香港机 nginx + 本地 workerd + SQLite | **访客 100% 走这里** |
| `https://api.qingwu.ink` | Cloudflare Worker + D1 | 仍在运行、**写接口仍开放** |
| `qingwu-blog.vercel.app` | Vercel 静态站 | 仍在（大陆不通，未验证是否还自动部署） |

「友链通过 → 回写 D1」这句话因此有了歧义：回写哪一份？

## 证据（2026-11-10 08:00 实测）

**① 远程 D1 与本地库的行数完全一致，且等于导出那一刻的快照**

| 表 | 远程 D1 | 本地导入时 |
|---|---|---|
| comments | 4 | 4 |
| applications | 9 | 9 |
| hits | 72 | 72 |
| link_feeds | 14 | 14 |

本地库是 2026-11-09 22:42 用 `wrangler d1 export` 导入的。**导出之后远程一行都没增加** ——
否则现在的行数会大于导入时的数字。⇒ 远程库自那一刻起就是冻结的。

**② 远程各表的最后写入时间都早于切换时刻**

| 表 | 最后写入（北京时间） |
|---|---|
| hits | 2026-11-02 11:09 |
| applications | 2026-11-06 17:05 |
| comments | 2026-11-09 16:55 |
| link_feeds | 2026-11-09 20:51 |

**③ 顺带发现一个独立故障：打点从 11-02 就断档了**

`hits` 只到 2026-11-02，之后 8 天 0 行；而 `daily_stats`（从旧 stats.json 迁移的历史汇总）
最后一天是 2026-10-17、397 pv。`/stats` 的 `pv = count(hits) + sum(daily_stats.pv)`，
所以 483 = 397 + 72 是**帐对得上的**，不是算错。

也就是说：11-02 之后 Vercel 线上那条打点链路静默失败了整整一周，直到 11-10 搬到家门口
又被同类问题咬了一次（`wrangler dev` 改写 Origin，见 README-hk 坑 #9）才被发现。
**这条与主从无关，即使不搬家也该修。**

## 为什么主库是本地，不是 CF

1. **访客已经全在本地。** apex / www / 裸 IP 全部 301 到 `www.qingwu.ink` → 香港机。
   CF 那份就算当主库，也没有流量能喂它。
2. **写延迟差一个太平洋。** 远程 D1 的 `served_by_colo` 是 **LAX**（洛杉矶），
   本机到香港 RTT 才几十毫秒。
3. **本地 schema 更新。** `mail_outbox`（0012）、GeoIP 的 `X-Q-Country` 都只在本地跑过，
   CF 那份没跑 0012。
4. **搬迁方向是单向的。** 从 CF 出来只要 `d1 export` 一次；再搬回去成本更高。

## 后果与待办（按优先级）

1. **✅ `api.qingwu.ink` 已降级为只读（2026-11-10 08:16 落地）。**
   Worker 新增 `Env.READONLY`（commit `439a7d2`）：非 GET/HEAD 请求一律
   `410 {"reason":"archived"}`，cron 也直接跳过（CF 上那条 `0 3 * * *` 原本每天写
   `link_feeds`，不停掉死库会自己长出「更新」假象）。开关以 **secret** 形式只配在
   Cloudflare（`wrangler secret put READONLY`），本地 `.dev.vars` 不配、行为不变。

   实测对照：

   | 请求 | 结果 |
   |---|---|
   | `POST https://www.qingwu.ink/api/hit`（浏览器 UA） | `{"ok":true,"counted":true,"mode":"d1"}` 200 |

   | `GET https://api.qingwu.ink/health` | 200（观测保留） |
   | CF D1 `hits` | 仍 72 行、max `ts` 停在 11-02，**没被写脏** |

   （`qingwu-api.1454109769.workers.dev`）。国内访问超时、海外可通，同样是只读。
   要回滚：`wrangler secret delete READONLY` 即可（secret 立即生效，不用重新部署）。
2. **Vercel 项目要么断开 git 自动部署，要么明确只作演示站。**

## 万一要回 CF（回滚路径）

```bash
# 1. 导出本地库
cd /data/qingwu/worker && node node_modules/wrangler/bin/wrangler.js \
  d1 export qingwu --local --output /tmp/local.sql

# 2. 恢复 routes 并部署 Worker
#    worker/wrangler.toml 里取消注释 routes = [{ pattern = "api.qingwu.ink", custom_domain = true }]

# 3. 导入远程（先清库或建新库，别直接覆盖）
export CLOUDFLARE_API_TOKEN="$(tr -d '\r\n' < .cf-token)"
node node_modules/wrangler/bin/wrangler.js d1 execute qingwu --remote --file /tmp/local.sql
```

注意：远程 D1 从没跑过 `0012_mail_outbox`，回滚前要先 `migrations apply --remote`。
