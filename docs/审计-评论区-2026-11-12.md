## 二、逐个问题

### ① 回复不过审（高危，线上存在）

`postFriendReply` 的 INSERT 写死 `status='visible'`，整条路径**没有 `moderateComment`**。
主楼判得很严（五类 + 阈值 + 拦截记录），但只要挂到某条留言下面回复，就是一条不过筛的通道：
广告、辱骂照样展示，`/admin/review` 的拦截记录里也查不到。

修复：与主楼完全同一套 —— 先判，命中落 `spam`，`recordModeration` 记一笔，且**不给他发通知邮件**
（别替一条广告去敲人家的门）。审核自己挂了照常放行，规则与主楼一致。

### ② 身份冒充（高危，线上存在）

```ts
const author = (v.v.name || account?.display_name || ...)   // 旧
```

看着是「允许本条覆盖」，实际等于**任何登录用户都能把自己写成任意名字**。
实测：带会话 POST `{"name":"爱弥斯","avatar":"https://evil.example.com/x.png"}` → 完全成功，
前台还因为 `isAiAuthor(name, avatar)` 给它打上了 AI 徽章。

三格表单在登录后本来就不显示了，这条口子没有任何产品价值。现在登录后署名/站点/头像**一律取档案**，
回复同理。历史数据也自动纠正（列表 JOIN 取账号当前档案）。

### ③ 点赞双票（中危，线上存在）

点赞 key：未登录 `IP|UA 哈希`，登录后 `a<id>`。判重只查一种 ⇒ 同一条能点出两票。
实测：匿名点 → 1；登录点 → 2。

现在判重、取消、列表里的「我点过没」同时认两种 key。实测修复后：登录前点过，登录后点一次是**取消**（回到 0），
不再叠加。

### ④ 删主楼不级联（中危）

`DELETE` 只 `UPDATE comments SET status='deleted' WHERE id=?`，回复留在库里且仍是 `visible`。
因为列表按 `parent_id` 分组，父楼不在就没地方挂 —— 结果这些回复**页面上看不见，但谁也删不掉**
（接口只能按 id 一条条删，而它们不在任何列表里）。

现在删主楼会连带软删整栋；删单条回复仍只删自己。

### ⑤ 300 条窗口被回复挤占（中危，量大才发作）

原查询 `ORDER BY ts DESC LIMIT 300` 把主楼和回复一起捞，再在内存里按 `parent_id` 分组。
回复也算这 300 条 —— 活跃楼里回复一多，老主楼被挤出窗口，然后**它下面的回复全部变孤儿、整栋楼消失**。
当前 17 条数据看不出，但这是迟早踩到的坑。

改成两条查询：先取 300 条主楼，再按这批 id 取它们的回复。

## 四、通过的部分（没发现问题）

- **越权**：删除判定 `账号 → delete_token`，两种凭据都对不上就 403；`replyTo` 校验了 `parent_id` 同楼，
  拿别栋楼的 id 发不出通知。
- **隐私**：所有 SELECT 显式列字段，没有 `SELECT *`；响应里从不出现明文邮箱；登录后留言不落明文。
- **限流**：6 条 / 10 分钟 / 访客，命中 429。
- **审核的 fail-open**：judge 挂了、超时、表没迁移一律放行 —— 不会因为上游抖动把留言板变哑。
- **删除是软删**，`status != 'deleted'` 在各处一致过滤；`spam` 在前台三条查询里都被排除。
- **迁移缺失的降级**：`currentAccount` 返回 `undefined` 时放行、列表 JOIN 失败退老查询、
  头像表不存在时上传返回可读提示而不是 500。
- **邮件**：全部 `ctx.waitUntil`，失败进 `mail_outbox` 机会式补发，不阻塞访客。

## 五、没改的（需要你拍板 / 已知限制）

1. **后台收件箱的统计口径与列表对不上**
   `listComments` 默认 `status != 'deleted'`，且含回复；而徽章统计是
   `SELECT status, COUNT(*) FROM comments WHERE parent_id IS NULL GROUP BY status`（只算主楼、含 deleted）。
   数字和条数会对不上。改起来要么统计加 `!= 'deleted'`，要么列表也限制主楼 —— 取决于你想要哪种口径。

2. **审核没有配额闸**
   主楼和回复现在都判，`moderateComment` 不走 `quotaGate`。留言板本身有 6 条/10 分钟兜着，
   但被刷时 judge 的 API 消耗没有上限。要不要给访客路径也加 `AI_DAILY_LIMIT` 这类硬闸？

3. **限流对登录用户也按 IP**
   `ip_hash` 一律是 IP+UA 哈希，NAT / 校园网下多人共用一个出口，10 分钟只有 6 条。小站无感，人多会误伤。
   可以给登录用户改成按 `account_id` 计。

4. **没有分页**
   主楼 `LIMIT 300`，超过之后老的直接不显示，也没有「加载更多」。等真到 300 再说。

5. **点赞的旧匿名票不会迁移到账号**
   修复后同一个人不会再投两票，但历史数据里他可能留了一行匿名票。若他登录后点「取消」，
   会把那一行删掉（正确）；只是计数偶尔会差一两个。

6. **本地没有 AI key**
   `moderateComment` 在本地直接返回 `null`（未配置即放行），所以「拦截 → 落 spam → 记一笔」
   这条链路**没能实地跑通**，只验证了代码路径与主楼一致。上线后建议发一条明显的广告回复确认。
