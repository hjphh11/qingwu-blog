# 决策：评论系统不迁 Waline（2026-11-09）

> 状态：**已决** — 不引入 Waline，文章评论沿「复用 D1 `comments` 表」的路走。
> 当时也**没有动手实现**（用户选择先不写代码），本文件只留判断依据。

## 起因

问：评论系统能不能换成 / 更新成 Waline，有必要吗？

先要纠正一个前提：**项目从来没有文章评论系统**。`src/pages/blog/[slug].astro`
里没有任何评论区块，读者读完全文即到底。`docs/制作方案.md` 6.5 写的是
"可选（如 Giscus/Waline）"，`docs/HANDOFF.md` 标"未做"。所以这不是"换"，
是"从零加"。

## 关键事实：地基早就浇好了

评论的数据层与服务端**已经存在并在跑**，只是被友链留言板占用着：

| 资产 | 位置 |
|---|---|
| `comments` 表：`post_slug` 分区、`parent_id` 楼中楼、`status` 审核、`ip_hash` 限流、`idx_cmt_post` 索引 | `worker/migrations/0001_init.sql:74` |
| 补列 `email / author_url / avatar`，新增 `friend_likes`（按楼层去重） | `0007_friend_board.sql` |
| 回复 `@` 与邮件通知字段 `notify` | `0009_reply_notify.sql` |
| 整套服务端逻辑（列表 / 发帖 / 回复 / 点赞 / 删除 / 6 条·10 分钟限流 / CORS / `ctx.waitUntil` 异步发信） | `worker/src/friends-board.ts` |

`friends-board.ts` 第 22 行 `const SLUG = 'friends'` 是**唯一**把这张表锁在友链区的东西。

## 两条路的账

### Waline

优点：开发量近乎为零。Markdown、表情、@提醒、浏览量、`/ui` 管理后台、
Akismet / Turnstile、社交登录全现成；将来把博客搬离 Cloudflare 时评论能跟着走。

代价，按重要性排：

1. **国内可达性倒退。** Waline 前后端分离，前端必须跨域请求服务端。官方路径是
   Vercel 项目（`*.vercel.app` 或 CNAME 到 `vercel-dns.com`），国内不稳。
   而本项目当初正是因为 "workers.dev 在中国大陆 TCP 443 超时"，
   才把 API 绑到自家 zone 的 `api.qingwu.ink`（见 `worker/wrangler.toml` 注释）。
   上 Waline = 把刚填的坑再挖一次。
2. **官方跑不了 Workers。** Waline 依赖 Node 运行时；想落 Cloudflare 只能用社区的
   第三方实现 `Waline_On_Worker`（D1 版）——为了少一个依赖反而多一个非官方仓库。
   正规路径是 Vercel + Neon Postgres（新方案）或 LeanCloud / MongoDB / MySQL / SQLite，
   即多一个部署点、多一套账号、多一个数据库。
3. **数据分裂。** 评论进 Neon/LeanCloud，统计 / 友链 / 点赞在 D1。后台是独立 Express，
   得读两处；而 0007 的设计意图恰恰是"评论与友链留言共用一张表"。
4. **视觉最外来。** Waline 是 Vue 组件，DOM 不受控。玻璃卡片、`crimson #c23a55`、
   本地子集化的马善政 / 站酷小薇字体都要逐条 override，还要过 `check-tokens.mjs`，
   且其升级可能破样式。
5. **局域网自建版**要再跑一份（Docker + SQLite 可行，但又是一套东西）。

### 复用现有地基

把 `SLUG` 参数化成 `/comments/:slug`（或 query），
前端照 `src/components/FriendsBoard.tsx` 抄一个 `PostComments`，
后台按 `post_slug` 筛。数据仍在 D1，和统计 / 友链 / 点赞 / 后台一套。

这正是 `docs/后台迁移-Cloudflare方案.md` 第 5 步原本规划的路
（`POST /comments` + Turnstile 防刷 + 首条进 `pending` 审核）。

## 结论

**不换 Waline。** 要的功能 80% 已在自家库里跑着，剩下 20% 是"把 `friends`
换成文章 slug"——比接 Waline 便宜，且风格、后台、数据统一。

**唯一的反例**：如果哪天判断"不想再写代码"的收益大于一致性收益，
Waline 可以上，但**部署在能控的国内可达位置**（局域网 `192.168.10.216`
用 Docker + SQLite，绑 `waline.qingwu.ink`），不要落 Vercel。

## 真要动手时的顺序

1. `worker/src/friends-board.ts`：`SLUG` 改为入参；路由 `/friends-board` 保持不动
   （向后兼容），新增 `/comments/:slug` 系列。
2. 前端 `PostComments.tsx`：抄 `FriendsBoard.tsx` 的头像 / 时间 / 楼中楼 / 点赞 / 玻璃卡片，
   去掉"站点地址 / 友链申请"字段。
3. 后台：按 `post_slug` 的列表与审核（复用现有 pending 流程）。
4. 局域网自建版：`server.py` 补同名字段的路由。
